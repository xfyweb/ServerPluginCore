# 市场授权设计:永久授权 + 维护窗口(Perpetual + Maintenance)

- 状态:**已接受(设计)**
- 日期:2026-09
- 关联:ADR-001(信任模型)、ADR-003(市场开源)、api-contract.md(manifest schema 2)、manifest-design.md(signature 字段)、ROADMAP(P4 签名与市场)
- 实现阶段:P4-A(下载控制面)+ P4-B(授权模型)

## 1. 目标与设计前提

为 ServerPluginCore 的插件市场(registry)定义**付费插件的授权与分发模型**。本设计的出发点是一组明确的前提,它们决定了模型形态:

1. **插件源码可读性 ≈ 公开**。能力插件是 QuickJS 沙箱内的明文 JS(esbuild bundle 不做混淆,反格式化即还原),驱动插件是 Node 明文代码;高级语言 + 必须在用户机器上执行 ⇒ 运行时内存即可提取。**"把代码藏起来"在本平台不可行,也不应投入。**
2. **安全边界是能力不是代码**。沙箱权限 + 权限注册表 + 审计(ADR-001/ADR-005)约束插件"能做什么";市场授权只回答"用户能否获得某版本",两者正交。
3. **购买即源码**。既然付费用户拿到的就是可读代码,防"过期用户继续运行旧版本"没有意义 ⇒ **不设运行期吊销,不依赖持续心跳**。
4. **下载是天然在线点**。获取新版本必须经过 registry,授权检查只发生在下载时 ⇒ 无需常驻授权通道。

## 2. 授权模型:永久授权 + 维护窗口

两条正交语义:

- **对"已获得的版本":永久授权**——购买时即获得当前版本及此前全部历史版本的永久使用权,可反复下载、可运行、无过期;
- **对"获取新版本的资格":维护窗口**——许可证有效期内发布的更新,在发布时自动获得授权;窗口结束后不再获得**新发布版本**的授权。

```
购买点 T₀ ─────────────────────────── 维护截止 M ────────────▶
   │  v1.0 发布:授权 ✓                 │
   ├─ v1.1 发布(≤M):自动获得 ✓         │
   ├─ v1.2 发布(≤M):自动获得 ✓         │
   └───────────────────────────────────┤
   v1.3 发布(>M):不可获取 ✗             │
   │  但 ≤v1.2 的版本永久可运行、可重下    │
```

设计命名即"限时永久授权"——永久的是已获得的版本,限时的是维护服务。

## 3. 数据模型

授权判定基于**版本发布时间**而非授权时间,避免"窗口内买的版本,其补丁在窗口后也下不了"的边界扯皮:

```jsonc
// registry release(每个版本一条,不可变快照)
{
  "pluginId": "official:example",
  "version": { "code": 12, "name": "1.2.0" },
  "releasedAt": "2026-09-01T00:00:00Z",   // 发布时间(授权判定锚点)
  "bundleSha256": "...",                   // 代码哈希(签名对象的一部分)
  "signature": { /* manifest+代码签名,见 manifest-design */ }
}

// registry license(一次购买一条)
{
  "orderId": "ORD-20260901-0001",
  "pluginId": "official:example",
  "purchasedAt": "2026-09-01T00:00:00Z",
  "maintenanceUntil": "2027-09-01T00:00:00Z"   // 维护窗口截止
}
```

**核心判定(仅下载时执行)**:

```
可下载 version V ⟺ V.releasedAt ≤ license.maintenanceUntil
```

- 维护期内发布的版本:可下载(含窗口最后一天发布的);
- 窗口结束后发布的版本:拒绝,返回 `UPDATES_EXPIRED`;
- **已获得的版本(含过期后)**:永远可重下——`releasedAt ≤ maintenanceUntil` 的版本对过期 license 一律放行,支持换机/重装。

## 4. 边界语义(决策记录)

| 场景 | 行为 | 理由 |
|---|---|---|
| 过期用户继续运行旧版本 | **允许,永久** | 代码本就可读,禁不掉也不该禁 |
| 过期用户重下维护期内版本 | **允许** | 他买断过这些版本;换机/重装不应被惩罚 |
| 过期用户下载新版本 | **拒绝**(UPDATES_EXPIRED) | 维护窗口是唯一收费锚点 |
| 分享/转发已购版本 | **不设技术防** | 源码可读;可选订单水印做追责(吓阻非技术性二次分发) |
| **设备绑定/指纹** | **不采用** | 源码可读下设备数防不了真盗版,反而干扰换机、增加隐私负担;下载配额已足够兜底 |
| **心跳/持续鉴权** | **不采用** | 无吊销对象、无续期对象;唯一在线点(下载)已覆盖授权检查 |

## 5. 全链路

```
购买 → 付款回调 → registry 生成 license(orderId/pluginId/maintenanceUntil)
     → 签发 download-token(短时、绑 order)
用户 → GET /download?version=v1.2 + token
     → registry 判定:license 有效 ∧ version.releasedAt ≤ maintenanceUntil
     → 返回 bundle + manifest + 签名(验签后安装)
运行 → 零联网:核心启动时本地验签 bundle 完整性(防篡改,内置官方公钥)
     → 沙箱内插件只读注入 license 上下文({orderId, pluginId, maintenanceUntil}),无网络授权路径
```

## 6. 下载控制面(防无限下载 / 防滥用)

下载是公开的带宽资源,免费与付费插件都必须控制——**不依赖登录,依赖配额**:

| 层 | 机制 |
|---|---|
| 下载令牌 | 公开 API 换取短时 download-token(60s);单 token 使用次数上限;防爬虫直拖 |
| 签发配额 | 单 license/单 IP 每日签发上限(如 5 次),超限 429 + 滥用计数 |
| 版本配额 | 单 IP × 版本窗口内下载次数上限;全局令牌桶限速 |
| 更新通道合一 | 插件更新走核心内置 update 通道(带签名校验),不开放裸文件托管——更新通道天然是限流点 |
| 滥用熔断 | 超限记 `abuse_log`,达到阈值临时封禁 IP/license |

免费插件走**匿名通道**(同配额限流,无需凭证);付费插件 download-token 额外绑定 license。

## 7. 与核心的集成

- **registry 客户端是核心侧模块**,不在沙箱内——授权判断与签名验签必须在核心侧执行,沙箱插件不可自验签(可被改写);
- 插件启动前,核心校验:manifest 签名合法(防篡改)+ bundle 哈希匹配;付费插件另查本地 license 缓存,未激活 → 拒绝加载并提示 `LICENSE_REQUIRED`;
- license 缓存(本地文件)用于离线重装场景:已获版本的重下不要求在线激活,仅 download-token 换发需在线。

## 8. 阶段划分

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **P4-A 下载控制面** | registry + 账号(可选)/匿名双通道 + download-token + 配额 + 版本发布 + ed25519 验签安装流 | ROADMAP P4 现有条目 |
| **P4-B 授权模型** | license 表(orderId/pluginId/maintenanceUntil)+ releasedAt 判定 + 付费下载端点 + UPDATES_EXPIRED | P4-A;首个付费插件形态确认后细化 |

## 9. 明确不做

- 本地代码加密 / 混淆 / 闭源加载器(高级语言运行即暴露,见前提 1);
- 机器绑定解密、持续心跳、运行期吊销(无对象、无意义,见 §4);
- 设备指纹与设备数限制(干扰正版,防不了盗版);
- "challenge 后拉取关键代码"式代码后置(源码可读前提下是负资产)。

## 10. 遗留问题(registry 服务端实现时定)

1. 付款/退款流程与 license 生成(支付网关未选型;退款 → 立即关闭维护窗口,已购版本保留);
2. 维护窗口定价与续费(窗口可叠加?续费从到期日顺延还是购买日顺延);
3. 订单水印的落地形态(若做追责,注入点与格式);
4. 免费插件与付费插件在 registry 上的可见性/徽标策略(与 ADR-003 双档一致)。
