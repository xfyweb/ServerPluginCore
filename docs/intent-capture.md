# 用户意图捕获与双通道权限模型（Intent Capture）

- 状态：**设计基线**（意图模型与默认安全边界已定稿：§7 判据/档位、§8 授予面；接口现在定，P3 落地）
- 关联：ADR-001 v4（意图信任根在前端）、ADR-002（核心前端与 Web Shell）、ADR-005 v3（主题包 / iframe 前端）、api-contract（前端 API）、manifest-design（`intent` 声明）、plugin-lifecycle-design（前端产物）
- 定位：回答"**用户意图怎么安全地到达核心**"，以及"插件能替用户做多少事"。

## 0. 一句话

**用户意图只能由可信前端捕获**；授权有两个来源——管理员预先授予（长期，管插件自主行为）与用户实时确认（短期，管用户此刻想做的事），两者最终都在核心侧校验后执行。

## 1. 三条通道

| 通道 | 起点 | 认证 | 授权来源 | 能否碰用户资源 |
|---|---|---|---|---|
| **前端通道** | 核心 Web Shell（**可信**） | frontend-token（用户会话） | **用户在核心 UI 的实时确认** | 能：确认即授权，核心前端**直接调核心 REST**，不经任何插件 |
| **插件通道** | 插件后端（沙箱，**不可信**） | 沙箱桥（宿主侧强制） | ① 管理员预先授予的权限点 ② 用户确认签发的 grantId | 只能：能力边界内 + 持 grantId 的资源操作 |
| **管理通道** | CLI（本地） | daemon 握手（ed25519 临时密钥） | 本机管理员 | **只做插件/主题管理**，不承载业务操作（TUI 落地后复用前端通道） |

要点：**核心自己做得到的操作根本不进插件**。删除文件、建立会话、重启服务这类核心原生能力，用户确认后由核心前端直连 REST 完成；插件只在"它自己是执行者"（Docker、MC 服务器等自有能力）时才介入，而那时它必须持 grantId。

## 2. 不变量

1. 插件**不产生**意图，也不**解释**意图——只传递与使用凭证；
2. **插件 UI 里的"点击"不构成授权**（可伪造），插件前端的任何请求都必须回到**核心渲染的确认窗口**才生效；
3. 核心前端是浏览器侧唯一意图捕获点；CLI 是**管理意图**的场所（只管插件与主题）；
4. **核心 UI 与插件 UI 必须视觉可区分**，且安全关键 UI（确认窗口 / 来源角标 / 提权输入）的呈现**不受主题与插件影响**。

## 3. 双源授权

```
自主发起（插件自有逻辑）  → 权限点：manifest 声明 + 管理员预先授予        长期
代理执行（用户此刻意图）  → grantId：核心签发，绑定 资源+操作+时效+受众   短期 / 一次性
```

- **核心原生能力**（fs、会话、服务、敏感命令）→ 核心执行，插件最多提供视图；
- **插件自有能力** → 插件后端执行；涉及用户选中资源时必须持 grantId；
- **资源类操作不受管理员作用域限制**：用户选中的路径可以在插件 manifest 声明的作用域之外（否则"插件的限制会变成对用户的限制"）；
- **安全底线仍受**：`/proc`、`/sys`、`/dev`、socket 与设备节点、管理员显式 deny 列表；
- **提权**：若前端能经 `sudo` 之类合法方式提权，**不阻拦**——这属于"用户意图 + 用户自带的凭据"；凭据只驻内存、绝不落盘，审计只记摘要。

## 4. grantId 规范

```ts
interface Grant {
  grantId: string;                    // 随机（防枚举）
  audience: string;                   // 只允许哪个插件使用（pluginId）
  operation: string;                  // read | write | delete | session:open | exec:sudo …
  resource: { kind: 'path' | 'session' | 'template'; ref: string };  // realpath / sessionId
  issuedBy: 'user';                   // ★ 只有"用户确认"能签发；管理员预授权走权限点，不签发 grantId
  userId: string;
  issuedAt: string;
  expiresAt: string;                  // 离散读 60s；长任务绑任务生命周期（另设 10min 硬上限，见 §8.7）
  oneShot: boolean;                   // 离散操作默认一次性；会话类绑定 sessionId 可复用
  signature: string;
}
```

- **签发密钥**：核心**持久化实例密钥**（状态目录 `intent-key`，首次启动生成）。不能复用 daemon 的临时内存密钥——重启即失效，会话类 grant 无法校验。CLI 握手仍用临时密钥，两者用途分离。
- **签发端点只接受前端的 frontend-token**；插件后端无权签发（"插件后端请求签发 grantId"是最直白的越权尝试，必须在此处断掉）。
- **校验**：验签 → `audience` 等于调用插件 → `operation` 匹配 → 资源（realpath 后）一致 → 未过期 → 一次性未消费（消费记录 + 审计）。
- **与 `grants: string[]` 的关系**：管理员授予保持"权限点列表、长期"，**不生成 grantId 实体**——长期凭证只有一种，避免两套模型并存。

## 5. 前端两层结构与通信协议

```
核心 Web Shell（核心代码，可信）
├── 路由 / 布局 / 菜单 / 主题系统 / i18n
├── 意图捕获 UI：资源选择器 · 确认窗口 · 来源角标 · 提权凭据输入
├── frontend-token（只在核心前端内存）
└── 插件容器
    ├── 声明式页面：manifest 声明组件树 JSON → 核心渲染（插件代码不执行）★ 最安全
    └── iframe 页面：插件 bundle，`sandbox` 隔离 ★ 最灵活
```

**iframe 细节（写死，避免实现踩坑）**

- `<iframe sandbox="allow-scripts">`——最小集。**不给** `allow-same-origin`（opaque origin 是本模型基石；且它与会话同源同时存在时 iframe 可自行移除 `sandbox` 属性）、`allow-popups`、`allow-top-navigation`、`allow-downloads`（下载即外发）、`allow-forms`、`allow-modals`；
- opaque origin ⇒ `localStorage` / `IndexedDB` / `cookie` 全不可用，请求带 `Origin: null` → **插件前端不得依赖浏览器存储**；
- **通信走 `MessageChannel` 私有端口 + 一次性 nonce 握手**；校验 `event.source === iframe.contentWindow`。**不要依赖 `event.origin`**——opaque origin 的它恒为 `"null"`，校验等于没校验；
- **插件前端不直连核心 API**：一律 `postMessage` → 核心前端 → 核心 REST（由核心前端代理并附 frontend-token）；
- 核心控制插件文档的响应头，因此 CSP 与 `sandbox` 属性**插件无法覆盖**。

## 6. 意图负载与出网边界（三层防御）

> 问题：插件从前端拿到用户意图后要传回自己的后端；若前端能任意发网络请求，敏感内容（文件列表、文件内容）就可能被直接外发，或借沙箱外发。

**结论：不做内容级流向追踪**（跨不可信域不可判定——插件合法地回传字符串，我们无法区分"用户选项"与"分块外泄的数据"；长度限制只是启发式，分块即可绕）。改为三层结构性防御：

### 6.1 第一层：iframe 零出网（硬边界，浏览器强制执行）

核心在服务插件文档时下发：

```
Content-Security-Policy:
  default-src 'none';
  script-src 'self';          /* 或 nonce */
  style-src 'self';           /* 不给 'unsafe-inline'，否则 CSS url() 就是外发通道 */
  img-src data: blob:;        /* 不给远程 img */
  font-src 'self';
  connect-src 'none';         /* fetch / XHR / WebSocket / EventSource / sendBeacon 全断 */
  form-action 'none';
  frame-ancestors 'self';
  base-uri 'none';
Permissions-Policy: camera=(), microphone=(), geolocation=(), …
```

**"插件前端直接把内容传给恶意后端"在浏览器层就被关掉**——不需要我们追踪任何数据。

### 6.2 第二层：意图结构化——默认只给"引用"，不给"内容"

插件在 manifest 里声明它能收到什么形状的意图，核心代理层按声明校验：

```jsonc
"intent": [
  { "name": "pickFile",   "kind": "selection", "resource": "path", "types": ["file"], "maxBytes": 512 },
  { "name": "targetPath", "kind": "text",      "maxLength": 256 },
  { "name": "mode",       "kind": "enum",      "values": ["fast", "safe"] }
]
```

1. 意图负载**只能是声明过的形状**：`selection`（资源**引用** + 元数据摘要）｜`text`（短字符串 + 长度上限）｜`enum`。**不接受任意 JSON、不接受嵌套、不接受 blob**；
2. 违反 → `INTENT_SCHEMA_VIOLATION`：拒绝转发 + 审计（这也是给管理员与市场审核的信号）；
3. **资源内容默认不随意图下发**：插件拿到引用 / grantId；要内容必须带 grantId 调沙箱 API 取——核心按 grantId 决定给什么、给多少，并记账；
4. 声明即审核面：管理员安装时能看到"这个插件会收到什么样的用户输入"。需要文件内容的插件（编辑器类）必须显式声明。

### 6.3 第三层：出网能力 = 唯一的 exfil 闸门

数据一旦进入插件后端，只剩一条外发路径：**用宿主 API 把数据带出去**。因此"谁能把数据带出去"有确定答案——**看它的权限点清单**。

**核心不向插件暴露网络原语**：不仿真 `node:net`/`http`/`dns`/`tls`，不提供裸 socket，也**不设 `net.*` API**（ADR-005 §5「不提供 net 裸 socket」、api-contract §4）。出网只有两条路，且**两条都是显式权限点**：

- ① **`exec` 模板**（核心提供）：静态可审查的数据 + E1–E10 + 管理员逐点批准——出网类模板（`git.pull`/`git.fetch`）必须单独批准；
- ② **驱动插件注册的端点**（插件提供）：db / SSH / Docker 这类协议能力，以及**任何 HTTP/通知类出网需求**——网络与 db/ssh 同级，一样外置（见 §6.6）；
- **能力级管控 + 每次外发可归因**（谁、哪个插件、多大、什么时候、走的哪个模板/端点）。

> 与"核心自身出网"区分：核心为了市场下载与密钥状态文档拉取（plugin-signature-design §6）**必须**有 HTTPS 客户端，但那只服务核心自己的运维行为，**不构成插件的能力面**、不进权限注册表。

### 6.4 第四层（免费）：声明式页面天然免疫

敏感数据（文件列表、服务列表、日志、配置）**默认走声明式页面**：数据在核心进程与核心前端之间流动，**插件代码从不接触**。

| 场景 | 走哪条路 |
|---|---|
| 列出文件、看配置、看日志、看服务状态 | **声明式页面**（插件不接触数据） |
| 需要选择资源（"选这个文件去备份"） | 核心选择器 → 意图只回**引用** → 插件用 grantId 取 |
| 终端 / 编辑器 / diff（必然接触内容） | iframe + 声明 `intent.text` + 出网能力受权限点约束 + 审计 |
| 富交互但不碰敏感数据（图表、表单、向导） | iframe（它拿不到不该拿的东西） |

判据：**"这个 UI 需要看到数据本身吗？"** —— 不需要 → 声明式；需要 → iframe，且它的出网能力必须能在权限点清单里被一眼看穿。

### 6.5 不做的与轻量可做的

- **不做**内容级 taint / 流向追踪（不可判定）；
- **不做**纯长度限制当边界（分块可绕）；长度只作为**滥用降级**；
- **可做**：① 核心代理给"插件前端 → 后端"的消息加体积与频率配额；② 每条意图消息记 `{pluginId, intentName, bytes}` 入审计（事后取证）。

### 6.6 通知 / HTTP 类出网：官方 net 驱动（**已定**）

§6.3 的两条路都能走通，但**都不便宜**——这类需求和"远程文件 / 远程终端"不是一回事，它要的是**出站 HTTP**：

| 需求 | 走 `exec` 模板 | 走第三方驱动插件 |
|---|---|---|
| 备份完成推一条钉钉 / Slack / 自建 webhook | 要一个 `curl` 类模板；而 **URL 是最难做参数校验的东西**（现有四种参数类型 enum/pattern/whitelist/path 都盖不住），且请求体会进 argv | 为发一条通知装一个**核心侧特权插件**（独立安装界面 + 最高强度提示），门槛过高 |
| DDNS 更新 / ACME 签证书 / 对象存储（S3/OSS）备份 / 拉外部健康检查 | 同上，且往往还要签名鉴权 | 同上 |

**决定：平台自己提供一个官方 net 驱动插件**（暂名 `@spc/net`）**随核心内置**（与核心同仓分发、默认安装），网络能力**外包**给它。

- **接口要窄**：只注册 `webhook.post`，或带域名白名单的 `net.fetch`（**禁重定向、禁 IP 字面量、体积/速率上限、审计**）；
- **为什么外包**：网络是最容易写错的安全面（SSRF / DNS rebinding / 重定向绕过 / TLS 校验 / 响应体炸弹），交给**一个可独立评审、独立更新的组件**承担，而不是焊进核心随核心发版；driver **不限制来源**，第三方可以写更好的并替换它；
- **出网仍是显式权限点** ⇒ §6.3 的闸门论证不变；
- **内置 ≠ 不可卸载**：它仍是普通插件，可禁用、可卸载、**可独立于核心更新**（ADR-005 §8 同时取消了 `reserved` 特性）。

**域名白名单沿用请求/批准分离**：插件在 manifest **声明**要访问的域名 → **管理员逐域名批准**（与 `grants` 同形的记录）→ **核心**负责"批准了哪些域名"（记录 + 展示 + 审计），**驱动**负责"按批准名单执行"（它本来就是被单独评审的特权组件）。

**入站监听：禁止**。插件与 driver 一律不得 `listen`；需要对外提供服务就用核心前端或用户自己的服务。（沙箱内本来技术不可能，但 driver 跑在核心侧、有 node API，所以这条必须明文写死。）

## 7. 确认窗口：判据、档位与强度

### 7.1 判据（二条件）

> **要确认 ⟺（意图经不可信方转述）或（点击时后果不可见）**

- **条件①：意图是否经不可信方转述。** 插件转述的意图（含 iframe 内的点击、iframe 内的键盘输入）核心无法确认"这一下真是用户点的、点的真是那个目标"，必须回核心确认窗口核对；用户在**核心组件**里亲手表达、亲眼看到目标的意图（文件选择器、删除按钮、设置表单）**不再重复确认**——那是把同一件事问两遍；
- **条件②：后果是否在点击前完整可见。** 不可逆、影响范围（如"是否连带删除关联卷"）、执行者、是否提权——只要有一项在点击时看不见，就要在确认窗口里补齐；全部可见则"知情即授权"，点击即执行。

两个条件都否 → 静默或仅提示。**确认不是"操作许可"，而是补足点击时看不见的信息**；对用户已经完整表达过的意图再要一次许可，就是纯粹的折损。

**推论（重要）：对插件的自主行为，边界是"拒绝 + 可审计"，不是"打断用户"。** 插件半夜自己去读越界路径，走的是权限点路径（管理员预授权的范围），越界就 `NOT_DECLARED` / `NOT_GRANTED` 拒绝并告警——**不弹窗**。弹窗只服务用户意图，不服务插件请求。**默认边界 ≠ 处处弹窗。**

### 7.2 四档与判定顺序

| 档 | 呈现 | 触发判据 |
|---|---|---|
| **L0 静默** | 无 | ① 完全在插件 self 域内（数据目录 / kv / timers / 自己的 events / lifecycle）；② 插件自主只读；③ 用户直选且**无副作用**（读 / 浏览 / 切视图） |
| **L1 提示** | toast + **撤销按钮** | 用户直选的可逆写（删除→回收站、覆盖→留备份副本） |
| **L2 确认** | 核心渲染弹窗：资源摘要 + **来源角标** + 补齐的后果 | ①成立；或不可逆写；或会话建立；或越出声明作用域 |
| **L3 二次确认** | 弹窗 + 确认词 / 提权凭据 | 提权（sudo、runAs）；递归 / 批量；爆炸半径不限单资源 |

判定顺序（**危险优先**，先命中先返回——fail-safe）：

```
0  安全底线命中（/proc /sys /dev、设备与 socket、管理员 deny 列表）  → 拒绝（不是确认）
1  提权 / 递归 / 批量 / 爆炸半径不限单资源                          → L3
2  意图经不可信方转述，或写操作不可逆                                → L2
3  用户直选的可逆写                                                  → L1（回收站 + toast）
4  其余（self 域内 / 插件自主只读 / 用户直选的读）                   → L0
```

（插件**自主**请求若越界，不进这条链——先在权限点判定处拒绝，见 §7.1 推论。）

与 §3 咬合：用户选中的路径在插件声明作用域之外时，**不再检查插件作用域，改检查 grantId**——用户的选择本身就是授权。

### 7.3 操作落点

| 操作 | 意图来源 | 档 | 备注 |
|---|---|---|---|
| 离散写（删除 / 复制 / 重命名 / 上传 / 覆盖） | 用户直选 | **L1** | 回收站 + toast 撤销；无法回收则降级为 L2 |
| 离散写 | **插件转述** | **L2** | 弹窗 + 资源摘要 + 来源角标 |
| 离散读（打开 / 浏览） | 用户直选（持 grantId）或插件自主已授予 | L0 | 读只可能来自"用户选择"或"管理员授予"，无第三种来源；`strict` 下升档 |
| 会话建立（pty / SSH / DB） | 插件转述 | **L2** | 一次确认 → 签发绑定 `sessionId` 的 grantId |
| 会话内敏感命令（`rm -rf` / `dd` / `sudo`） | 任意（含用户亲手敲） | **L3** | **强制点在核心/驱动端点**——能力插件没有 socket，命令流必经核心 |
| 持续交互 UI（终端、文件管理器界面） | — | L0 | UI 归插件，数据面归核心 |
| 插件自主只读（已声明 + 已授予） | 无用户参与 | L0 | 读之所以能放宽，前提见 §8.3 |
| 插件自主越界 | 无用户参与 | **拒绝** | 不弹窗，见 §7.1 推论 |

### 7.4 可逆性台账（用"撤销"替代"确认"）

避免"5 秒倒计时催你点撤销"的焦虑设计，改成**执行 + 真可逆 + toast 撤销**：

| 操作 | 可逆手段 |
|---|---|
| 删除 | **回收站**（trash 目录 + 还原）；超配额 / 跨设备无法入回收站 → 降级为 L2 |
| 覆盖 | 自动备份副本 `x.log.bak.<ts>` |
| 配置类（nginx reload / 服务重启） | 保留旧配置 + 一键回滚 |
| **真不可逆**：终端命令、DB DDL、停止 MC 服务器（玩家掉线）、外发数据 | 只能 L2 / L3 |

回收站需配额与保留期（未定：默认容量与天数）。

### 7.5 强度档位与蜜月期

配置：`intent.confirm = strict | normal | relaxed`（默认 `normal`），支持按操作类别覆盖。

| 档 | 规则 |
|---|---|
| `relaxed` | 用户直选路径连 toast 都省（仍记审计 + 仍留回收站） |
| `normal` | 即 §7.2 / §7.3 |
| `strict` | 全档升一级（L1→L2、L2→L3） |

**蜜月期**：新装 / 升级后首次运行 **24h 内按 `strict` 执行**，之后回落 `normal`。给管理员"新东西先盯着"的安全感，又不长期磨人。

## 8. 默认安全边界：插件声明的默认授予面

### 8.1 安装即一次授权

**安装插件本身就是一次授权行为**：用户在安装界面看到的权限清单就是他签的同意书。对只读类与插件自有能力再要求"逐点授予"，是把同一件事问两遍。因此权限点分三档：

| 档 | 覆盖 | 行为 |
|---|---|---|
| `auto` | 全部 `scope:self` + `lifecycle.*` | 安装即生效，清单可见；**免声明免授予，也撤不动**（够不着别人） |
| `install` | host 级**只读** + 插件自有能力（`docker.read`） | **首次安装时按清单播种进白名单**（`grants`），之后与 `explicit` **完全一样**；撤回 = 移出白名单（对运行中的插件需 reload 生效） |
| `explicit` | 写宿主资源、`exec.template.*`、`process.*`、驱动插件的出网类端点、**跨插件调用/订阅（`plugins.call.*` / `events.subscribe.*`）**、提权 | 默认拒绝，逐点授予 |

> **跨插件为什么是 `explicit`（2026-09-23 定）**：插件之间**默认隔离**（`exports` 默认私有、看不见别的插件），
> 调用别人的端点、监听别人的事件都是**跨过去**，只有"管理员逐条点头"对得上这个模型。
> 早先把它们划进 `install` 等于"清单里写一行就通"，与隔离默认相反。

落地形态：`PermissionPoint` 增加 `grant: 'auto' | 'install' | 'explicit'` 字段。**它与 v3 删除的 `protectionLevel` 本质不同——这个字段被判定链读取**（`protectionLevel` 是死字段，故删）。同时 `scope` 从"要不要授予"退为"碰不碰宿主资源"，并加**注册期**一致性约束 `scope: self ⇒ grant: auto` **与 `scope: host ⇒ grant ≠ auto`**（违反 → `SCOPE_GRANT_INVALID`），与既有的 `executionLevel ≥ confidentiality` 同属注册期校验——两个字段各有一处读取点，都不会变成装饰。

> **✅ 已落地（2026-09，第四批 B；2026-09-23/24 收敛）**：三档与注册期约束都在代码里（`core/permissions/registry.ts`）。
> 09-23/24 的体检收敛了三处：**注册期挡住 `host + auto`**（此前只有测试守着）；
> **`install` 与 `explicit` 合并走同一条白名单**（`install` = 首次安装时**播种**一次 —— 修掉"`revoke` 删一个
> 不存在的条目、判定照旧放行而 CLI 报成功"的假成功，顺带让升级新增点不再静默生效）；
> **`auto` 档的 `grant` / `revoke` 明确报 `GRANT_NOT_APPLICABLE`**，不再假装成功。
> 另：**驱动插件注册的点，档位与等级由驱动自己定**（核心不替它选；缺省 `host ⇒ explicit` 的 fail-closed 方向不变）。

### 8.2 判定链（替换 api-contract §7 第 3 步）

```
1  权限点查不到（冻结表 ∪ 临时表）                → UNKNOWN_POINT
2  manifest 未声明该点                           → NOT_DECLARED
3  grant != auto 且不在 `grants` 里              → NOT_GRANTED
4  通过（auto / install 审计记 grant 档）
```

### 8.3 为什么读可以放宽（唯一前提）

因为 §6.3 已把所有外发能力收进 `explicit`——**泄漏在出口处被切断，读就不再是危险动作**。这是整个分档能松的**唯一前提**；哪天真出现一条隐式出网路径，这张表会整体塌掉。§8.5 就是这个前提目前唯一的缺口。

### 8.4 增量同意（升级）

更新时**新增**的 `install` / `explicit` 点必须重新展示并取得同意，不能默认继承旧同意。拒绝授予不影响插件可用性——相关功能报 `NOT_GRANTED`，其余照常。

> ⚠️ **2026-09-24 更新**：这条现在**安全的那一半已经有了** —— `install` 与 `explicit` 合并走同一条白名单，
> 而 `install` 档只在**首次安装**播种一次 ⇒ 升级新增的点**不会**自动生效，会 fail-closed 停在 `NOT_GRANTED`
> 等管理员授予。缺的是**主动性**：新增点不会主动摆到管理员眼前（要靠调用失败才发现），落点见
> `docs/api-contract.md` §12-5。

### 8.5 事件总线：绕过出口闸门的第二跳

> 术语（2026-09-22）：这条通道现在的正式名字是**事件面**（不再是"总线"——核心不广播、也不发自己的流程事件），设计见 `docs/events-and-hooks-design.md`。本节的两条封堵**不变**，理由也不变：泄漏方是**发布方自己**（A 读到敏感数据 → 自己发布出去 → B 有出网），与"核心广播不广播"无关。

A（读到敏感数据）→ 事件 payload → B（有出网能力）→ 外发。**两跳外泄，闸门只拦一跳。** 已定封堵：

- ① **授出网权限时，同一屏强制显示"该插件订阅的 topic 清单"**——把两跳压成一屏可读，管理员看见链路后自行决定；
- ② topic 的 `classification` 参与授权：`secret` 类 topic 禁止跨插件。

（"事件 payload 也只给引用不给内容"留作以后真有事故再上。）

### 8.6 六个场景（验收用例）

| 场景 | 意图来源 | 后果可见 | 落点 | 用户负担 |
|---|---|---|---|---|
| **1 备份插件选文件**：核心文件选择器选 `/srv/mc/survival/world` → 选择器**当场签发最小操作 grantId**（`operation:'read'`，不给写权）→ 转发引用 → 插件持 grantId 读 → 写自己数据目录（`auto`） | 用户直选（核心组件） | 是 | L0 + 1 toast | **0 弹窗** |
| **2 删 Docker 容器**：iframe 内点击 → postMessage → 核心确认窗口（来源角标 + 目标 + 镜像 + **"同时删除关联卷"勾选框**，默认不勾）→ 签发 `docker.remove` grantId | 插件转述 | 否 → 由确认框补齐 | L2 ×1 | 1 确认 |
| **3 终端插件敲 `sudo systemctl restart nginx`**：pty 由核心持有 → 输入解析层命中 `sudo` → 核心渲染提权确认 + **核心渲染凭据输入框**（iframe 拿不到明文） | 插件转述（iframe 键盘） | 否（提权） | L3 ×1 | 确认 + 密码 |
| **4 插件半夜自主读 `/etc/shadow`**：无 grantId 路径 → 权限点路径 → manifest 未声明 → 拒绝；即使声明且授予，仍在安全底线 deny 列表内 | 无用户参与 | — | **拒绝 + 告警** | 0 |
| **5 新装 + 蜜月期 + 增量同意**：安装界面一屏列出三档清单（点"安装"= `install` 档生效）→ 首 24h `strict` → 需要 `process.start` 时逐点授予 → 升级新增**出网类权限点**（如 `exec.template.core:git.pull`，或驱动插件注册的端点）走增量同意 | — | — | 安装清单 + 逐点 | 1 屏清单 |
| **6 授出网**：授出网类权限点（exec 模板 / 驱动端点）时同屏列出该插件订阅的 topic（§8.5） | — | — | L2 + 订阅清单 | 同屏 |

对照要点：场景 1 与场景 3 都是"用户亲手做的"，**差别只在替用户执行的是不是不可信方**——这就是条件①的边界，不是例外。

### 8.7 场景暴露的两个接口缺口

1. **资源类 grant 的 TTL 不能只看墙钟**：场景 1 默认 60s，备份大目录必然超时。改为 **离散读 60s；长任务 grant 绑定"任务生命周期"**（任务终态即失效），另设 10 min 硬上限防挂——§4 的"默认 60s"据此修订；
2. **`grant.operation` 必须与 driver 注册的方法名对得上**（场景 2 的 `docker.remove`）：driver 注册时必须同时登记 `operation` 名，否则确认窗口签发的 grantId 校验不上——api-contract §10 的注册结构已点名。

## 9. 主题模型

主题不是"插件"，也不是纯 CSS，而是**声明式设计令牌 + 资源 + 受限样式，无 JS**：

```jsonc
// theme.json
{ "themeSchema": 1, "id": "@xfy2412/nord", "name": "Nord",
  "tokens": {                                  // 核心与插件 iframe 共用同一批变量
    "color.bg": "#2e3440", "color.fg": "#d8dee9", "color.accent": "#88c0d0",
    "radius.md": "8px", "space.unit": "4px", "font.sans": "Inter, system-ui",
    "density": "comfortable"                   // compact | comfortable | spacious
  },
  "icons": "icons.svg",                        // 图标集（symbol sprite）
  "assets": ["fonts/inter.woff2"],
  "css": "overrides.css",                      // 受限：只作用在 [data-spc-skin] 作用域内
  "layout": "sidebar"                          // 只做"选择"，布局变体由核心实现
}
```

- **可换**：颜色 / 字体 / 间距 / 圆角 / 密度 / 图标 / 资源 / 受限样式 / 布局变体的选择；
- **不可换**：安全关键 UI——确认窗口、来源角标、权限提示、提权输入框。核心给它们固定样式与**独立渲染层**，主题 CSS 限定在 `[data-spc-skin]` 内。否则恶意主题能画一个假确认框，直接把"视觉区分"这条防御绕过——**这是主题的安全边界，不只是美观问题**；
- **插件 iframe 也吃主题**：核心把 tokens 作为 CSS 变量 + `theme` 消息推给 iframe（插件用 `var(--spc-color-accent)`），两边视觉一致而无需共享 DOM；
- **无 JS** ⇒ 装 / 启 / 切换不需要沙箱与生命周期钩子（但进同一套安装记录：`type: theme`，用 `theme.json` 代替入口，**豁免 `init`**）；
- 留作后续（P5）：分区/插槽（主题只选排布变体，不能注入结构）、组件皮肤选择器白名单。

## 10. CLI 与 TUI 的定位

- 当前 CLI = **插件与主题管理**：`plugin install / enable / disable / reload / status / grant / revoke`、`theme list / enable`、`about / status`；
- **不承载业务操作**：业务操作是用户意图，走核心 REST；
- 未来 TUI = **前端通道的终端形态**（复用同一批核心 REST），那时业务操作才进 CLI；在此之前 CLI 就保持"只有插件管理"；
- 管理员预授权（插件通道的长期授权来源）自然落在 CLI。

## 11. 审计

意图类操作统一落：`{ ts, userId, channel: 'frontend' | 'plugin' | 'cli', pluginId?, grantId?, operation, resourceDigest, decision, result, durationMs }`；grantId 的**签发 / 消费 / 拒绝**各一条；资源只记摘要；提权凭据永不落盘。插件前端消息额外记 `{ intentName, bytes }`。

## 12. 攻击面与消解

| 攻击 | 防御 |
|---|---|
| 插件后端伪造 grantId | 核心持久密钥签名，验签失败 |
| 插件后端自行签发 grantId | 签发端点只接受 frontend-token |
| 插件前端伪造"用户点了删除" | iframe 内的点击不算授权，必须回核心确认窗口 |
| 插件前端窃取 frontend-token | opaque origin + 不直连核心 API + token 只在核心前端内存 |
| 插件前端读核心 DOM / 变量 | `sandbox`（无 `allow-same-origin`）+ CSP |
| 插件前端窃听消息 | `MessageChannel` 私有端口 + nonce + `event.source` 校验 |
| 插件前端外发内容 | CSP `connect-src 'none'` 等（§6.1，浏览器强制） |
| 插件借沙箱外发内容 | 出网能力受权限点 + 模板审查 + 审计约束（§6.3） |
| **经事件总线两跳外发**（A 读数据 → 事件 → B 有出网） | 授出网时同屏显示订阅 topic 清单 + `secret` 类 topic 禁止跨插件（§8.5） |
| 插件复用 grantId | 绑定 audience / operation / resource + 一次性 + 短时效 |
| 主题伪装安全 UI | 安全 UI 固定样式 + CSS 限定 `[data-spc-skin]` + 主题无 JS |
| 插件 UI 冒充核心 UI | iframe 视觉分区 + 来源角标 + 确认窗口独立渲染层 |
| **唯一实质残留** | **用户被欺骗点击** → 视觉区分 + 敏感操作二次确认 + 资源摘要展示 |

## 13. 前置依赖与未决

- **用户与会话身份**（硬前置）：本模型要回答"谁在确认"。本轮只留接口位——`userId` 字段、frontend-token 绑定会话；认证方式（单管理员 / 多用户 / RBAC）后续参考开源项目实现；
- **未决**：会话型 grantId 的续期与撤销语义（会话断开 vs grant 过期）；提权凭据的输入渠道与"是否记录已授权提权"；声明式页面的组件树 schema（P3 定）；回收站的默认配额与保留期（§7.4）；事件 topic 的 `classification` 分级细则（§8.5②）。
- **已定**：默认安全边界见 §7（确认判据 / 四档 / 强度 / 蜜月期）与 §8（三档授予面 / 增量同意 / 事件总线第二跳）。
