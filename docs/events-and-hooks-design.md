# 事件、调用与钩子设计（interop）

> **状态**：**§1 事件面 + §3 调用面 = P2 落地范围**；**§2 钩子链 = 结论保留、P2 不做**（等协作插件 `hook` 那一轮）。
> **依据**：ADR-001（零环境权力）、ADR-005（沙箱与插件类型）、`manifest-design.md` §6（插件间可见性）、
> `api-contract.md` §3/§6/§7、`intent-capture.md` §8.5（第二跳）、`plugin-signature-design.md`（源的 keyring / 完整引用 / 安装记录）。
> **取代关系**：本文重写 `api-contract.md` §3 的"事件总线"部分；§3 定了插件间调用与**带源身份**；
> 其余文档的同步清单、实施顺序与待定见 **§4**。

## 0. 一句话

沙箱里**没有"总线"**，只有**显式关系上的通道**：下面三件事各走一条，**都不允许一个插件偷偷碰另一个插件**。

| 面 | 一句话 | 章节 | P2 |
|---|---|---|---|
| **事件**（推） | 插件自己发布事实，**声明过关系**的插件收到；**核心只搬运**（不广播、不解释、不裁决） | §1 | ✅ 做 |
| **调用**（拉） | 插件按**完整引用**定向调用另一个插件的公开端点，**要结果** | §3 | ✅ 做 |
| **钩子** | 核心在**决策点**上回调插件、采纳它的答复（中间件，方向相反） | §2 | ❌ 不做 |

四条推论先摆在这里，后面所有条款都是它们的展开：

1. **"广播"不存在**：每一跳的收件人，在装载时就登记好了（清单声明 + 管理员批准）；
2. **核心不往里发东西**：插件调用了什么、核心做了什么，都不是事件；**发布永远是插件自己的动作**；
3. **核心不解释意见**：征询回来的意见**原样**交给发布方，采纳与否由发布方自己的代码决定；
4. **身份带源**：一个插件由 **`(origin, id)`** 唯一确定（`id` 与 `author.id` 都只是自述名字），
   所有跨插件的引用一律写**完整引用** `<origin>/@user/name` —— 见 §3.2。


## 1. 事件面（P2 做）

### 1.0 现状（2026-09-22 核对代码）

| 面 | 现状 |
|---|---|
| 清单形状 | ✅ `sdk/types.ts`：`exports.events.publish[]{topic, classification}` / `subscribe[]{topic, mode}` |
| 能力登记 | ✅ `core/plugin/capabilities.ts`：**一个 topic 只能有一个发布者**（第二个 owner → `PLUGIN_EXPORT_INVALID`）；登记 `published` / `subscriptions` 两张表；`capabilities` 记 `event:<topic>` / `subscribe:<topic>`；全有或全无、可精确撤销 |
| 发布 | ⚠️ **只有一半**：`core/hostApi.ts` 的 `events.publish` 校验 topic 在声明内（否则 `EVENT_TOPIC_NOT_DECLARED`），解码 payload、算字节数，返回 `{ ok, topic, bytes }` ——**payload 到宿主就停了**：没有订阅者、没有任何投递 |
| 订阅 | ❌ 不存在（只有登记） |
| 权限点 | ⚠️ 只有 `events.publish`（`scope: self` / `grant: auto`）；**订阅方向没有权限点** |

### 1.1 为什么不是"广播"

`manifest-design.md` §6 已经定了：**插件默认看不见其他插件；要订阅他人事件、或调用他人 Web API，必须在 `dependencies.plugins` 里显式声明**。
所以"核心把 A 的动作广播给所有订阅者"= 核心替 A 把它要干什么告诉了**没声明依赖 A 的第三方**，与那条规则直接冲突。
更根本的一点：插件之间是**声明过的、有向的关系**；插件与核心之间没有这层关系（所有插件都依赖核心）⇒ 核心发事件就是无差别广播。

Linux 在同一件事上的做法可以直接对照（下面几条都来自 Linux 6.12.110，见 §4.3 的引用口径）：

- **netlink / connector**：`cn_netlink_send_mult()` 只把消息投给**显式 join 过该组**的订阅者，而且"**没有听众**"是一等公民状态（返回 `-ESRCH`，不是异常流程）（`include/linux/connector.h:78-127`）；
- **inotify**：订阅方**自己声明 mask**（关心哪些事件位），每个观察者**自己的队列**，队列溢出本身就是一条事件（`IN_Q_OVERFLOW`）（`include/linux/inotify.h:12-18`）；
- 内核**从不对用户态广播"某个进程在干什么"**——根本没有这样的总线。

⇒ 我们要的形态就是这三条：**关系先显式建立、只投给声明过的人、每个订阅者独立可观测**。

### 1.2 命名空间与所有权

- **`core.` 是保留前缀**（核心将来要发的事实；P2 里核心不发任何事件）；插件只能用**自己的完整引用**开头：`<origin>/@publisher/name.<事件名>`（裸 id 不够 —— 同名不同源是两个插件，见 §3.2）。
  ⚠️ 这是**新增校验**：今天 `capabilities.ts` 只查"同 topic 的 owner 唯一"，插件完全可以抢注一个听起来像核心的 topic（如 `core.exec.before`）并成为它的 owner。要补"保留前缀 + 完整引用命名空间"校验，违反 → `PLUGIN_EXPORT_INVALID`。
- **一个 topic 只能有一个发布者**（已有规则，保持）。订阅方数量不限。
- 事件名是**英文契约**（与错误码同规矩）：渲染层翻译，核心不做本地化。

### 1.3 两种用法：通知与征询

| 用法 | 调用 | 语义 | 核心做什么 |
|---|---|---|---|
| **通知** | `events.publish(topic, payload)` | "我做了/我要做这件事"，**不等任何人** | 查收件人 → 投递 → 记审计 |
| **征询** | `events.request(topic, payload)` → `{ eventId, opinions }` | "**我想听听你们的意见**" | 查收件人 → 按序逐个问 → **把意见原样装成列表交回** |

- **一个 topic 支不支持被征询，由发布方在清单里声明**：`publish[].ask?: boolean`（**新增字段**，缺省 `false`）。
  对没声明 `ask` 的 topic 调 `request` → `EVENT_ASK_NOT_SUPPORTED`。
- 订阅方的 `mode` 语义写准：`notify` = **只听**；`arbitrate` = **我愿意出意见**（不是"我裁决"）。
  两边不匹配**不报错**，只是永远收不到征询。
- **同一个 topic 可以既被通知式发布、也被征询式请求**——由发布方的代码决定这一次要哪种。

### 1.4 场景走一遍（数据库刷新 + 定时备份）

数据库插件 `@a/sqlite` 声明发布 `refresh-started` / `refresh-finished`，备份插件 `@b/backup` 声明订阅、并声明依赖 `@a/sqlite`。

**用法一：通知（推迟备份）**

1. `@a/sqlite`：`events.publish('@a/sqlite.refresh-started', { at })`，**说完就走**；
2. 核心查登记表 → 收件人只有 `@b/backup` → 投递给它（此刻它空闲）；
3. `@b/backup` 把"正在刷新"记在自己状态里；定时器到点时看到这个状态，**主动推迟**；
4. 收到 `refresh-finished` 后恢复备份。

这条路径**不需要任何裁决机制**——发布方只管说，订阅方自己决定怎么办。

**用法二：征询（拒绝现在刷新）**

1. `@a/sqlite`：`const r = events.request('@a/sqlite.refresh-started', { at })`；
2. 核心按**管理员排的顺序**逐个进订阅方的 VM 收意见；`@b/backup` 返回 `{ decision: 'deny', reason: 'backup in progress' }`；
3. 核心把意见装成列表交回；`@a/sqlite` 的代码看到 `deny`，**自己决定**是推迟刷新、还是照样刷；
4. 核心全程**不拦、不改、不替它下结论**。

**恶意反复拒绝**：审计里每一次投递都有记录（谁、哪个 topic、第几次、什么意见、耗时）⇒ 管理员据此**逐 topic 撤销它的订阅**，或者禁用/卸载（见 §1.11）。

### 1.5 "核心只搬运意见"消掉了四类问题

| 原本要设计的 | 为什么不用了 |
|---|---|
| 多个 `modify` 怎么合成（链式改写还是冲突即拒） | 核心**不解释**意见：每条意见独立、原样交回，由发布方自己合 |
| 拒绝的"粘性"（后面的人不能推翻前面的拒绝） | 同上——没有"核心裁决"这回事，就没有粘性可言 |
| `deny` 要不要短路后续裁决方 | **默认问完所有人**，把全部意见交回 |
| 核心流程被插件卡住 | 等待的是**发布方自己**（它挂在 `request` 那次宿主调用上），核心流程不参与 |

> 这四条连同 §2 的整套规则，**都属于"核心强制裁决"的世界**——那是 hook / driver 的事，P2 不做。

### 1.6 意见的形状，与"没答"

**SDK 约定**（核心不解释，但要求一个最小形状，否则审计与发布方都没法用）：

```
{ decision?: 'allow' | 'deny' | 'defer' | string, reason?: string, data?: unknown }
```

- 核心**只保证它是 JSON**、只把 `decision` / `reason` 写进审计，**不因它改变任何流程**；
- 处理函数**可以不返回**（= 没意见）；
- 处理函数可以返回 Promise（宿主会等它，受 §1.9 的预算约束）。

**核心交给发布方的结果**：

```
{ eventId, opinions: [
    { pluginId, outcome: 'opinion', data, reason, ms },
    { pluginId, outcome: 'skipped', skipReason: 'busy'|'timeout'|'crashed'|'unloaded'|'revoked' }
] }
```

**硬规矩：核心不许把"没答"塌缩成"同意"或"拒绝"。** 缺席就是缺席，四种原因分开报：
`busy`（`PLUGIN_BUSY`，按既定串行契约**弃权**）/ `timeout` / `crashed` / `unloaded`（处理期间被卸载，延后拆保证了拿得到状态）。
**怎么解读缺席，是发布方自己的逻辑**（SDK 文档里建议保守处理，但核心不强制——见 §0 第 3 条）。

### 1.7 收件人、顺序、门槛

**收件人**（三个条件全满足才投）：

1. 该插件在清单里**声明订阅**了这个 topic；
2. 该插件在 `dependencies.plugins` 里**声明依赖**发布方（按 **`(origin, id)`**，见 §3.2；`manifest-design.md` §6；缺失 → 装载期 `PLUGIN_EXPORT_INVALID`）；
3. 管理员**批准**了这条订阅，且**没有撤销**（§1.10）。

**顺序**：管理员在 **Web UI 手工排**，**按 topic 各排一张表**（同一个插件在不同 topic 上可以排不同位置）。

- 没排过 ⇒ 按**装载序**，UI 上显式标"未排序"；
- **快照生效**：排序变更**在下一次投递才生效**，不改动正在跑的链；
- 顺序决定**问的次序**与 `opinions` 列表的次序（P2 不短路，所以它不影响结果，只影响可读性与耗时）。

**门槛只剩"听"这一把**（"拦"那一把属于 §2）：

- 事件的等级由**发布方逐次声明**（"这一次有多敏感"），没声明就按**清单登记**的 `classification` 兜底；
- 合成沿用已有实现：`effective = max(订阅方声明, 管理员覆盖, 清单兜底)`，**只升不降**（`core/permissions/check.ts` 的 `effectiveLevel`）；
- ⚠️ **现状缺口**（`api-contract.md` §7.1 已记）：桥调用判定时**没把 `meta` / `userOverride` 传进去**，也没有 `pathLevels` 配置 ⇒ 今天等于"每个权限点一个固定等级"。本设计要接线：宿主原语声明"这次碰的是什么"（`metaFor`）+ 管理员覆盖真的存在 + 审计记合成后的真值。
- ⚠️ **不要在仿真层（`node-*.js`）里判等级**：等级属于"碰资源的那一层"，与 `scope`/`grant` 同源。

### 1.8 payload 与二进制

- **只能是 JSON 能表示的值**。显式拒绝（fail-closed，**不静默丢字段**）：函数、类实例、Symbol、循环引用、`Map`/`Set`/`Date`/`RegExp`、Promise ⇒ `EVENT_PAYLOAD_NOT_SERIALIZABLE`。
- **体积上限**：JSON 部分与字节部分**分开计量**，超限 ⇒ `EVENT_PAYLOAD_TOO_LARGE`。没有上限的话，事件就是绕过文件读写限额搬运大文件的后门（`bytes` 今天已经在算，正好复用）。
- **二进制走单独的槽**，不塞进 JSON（照抄仿真模块的做法：`fs.readBytes` / `bytes.*` 走的就是这条通道）：
  - 沙箱 → 宿主：宿主方法参数本来就允许字节（`HostArg = string | Uint8Array`）；
  - 宿主 → 沙箱：用 `newArrayBuffer` 造句柄（与 `binaryResult` 同一条路）；
  - 契约不变：**ArrayBuffer = 数据，字符串 = 错误**。
  ⚠️ **要动投递链**：现在"宿主叫插件"只传字符串（定时器、文件监视都是），要加字节槽。
- 不在 JSON 里塞 base64：膨胀 33%，还要求两端各实现一套约定。

### 1.9 投递机制（复用现成积木，不发明新通道）

| 用法 | 走哪条现成的路 |
|---|---|
| **通知** | `fs.watch` 那条：宿主排队 → 唤醒插件（`bridge.deliver` 加第三种 `kind: 'event'`）→ 插件来取（`take`）→ 审计 `beginPhase` |
| **征询** | 生命周期钩子那条：从模块命名空间按名字取导出、宿主直调、可返回 Promise、有 deadline、有 `PLUGIN_BUSY` 守卫（与 `callHook` 同形） |

**订阅面**：清单里**声明**（授权面）+ 运行时 `events.on(topic, handler)` **绑定处理函数**。

- 为什么两条都要：`plugin-lifecycle-design.md` §3 定过"**manifest 是审核对象与唯一事实源；插件说了不算**"——所以**能不能发/能不能听**必须走清单，运行时的 `events.on` **只能绑已申报的 topic**（否则 `EVENT_TOPIC_NOT_DECLARED`）；
- 这是插件作者习惯的写法（Velocity 那类也是手动注册；我们不做装饰器——插件是纯 ESM，没有转译步骤）；
- 核心为每个插件维护**运行时钩子表**（`events.on` 过桥时登记）：投递前知道"有没有听众"（没听众就不用叫醒插件）、审计能记"实际绑了什么"、征询时知道该等谁；**插件卸载时这张表随之清空**。
- **处理中不许改登记**：链在遍历开始时做**快照**，处理函数里 `events.off()` 只影响下一次（照抄 Linux 明文禁止的"在调用链里注销"）。

### 1.10 权限点与档位

- `events.publish`：**已有**，`scope: self` / `grant: auto`（发布自己的事，够不着别人，保持不动）。
- **订阅他人事件要新增权限点**：**动态权限点 `events.subscribe.<发布方完整引用>.<topic>`**（带源的理由与拼法见 §3.4 —— 同 id 不同源是两个插件，点名不带源就等于两个发布方共用一条订阅授权），`scope: host`、**`grant: explicit`**。
  - 点由**发布方**登记 topic 时带出（不是订阅方），跟着 `capabilities.revoke` 一起消失：**发布方没了，就没有可听的东西**，授权不该留着；
  - **等级取发布方的 `classification`**（public → low、sensitive → medium）：管理员在安装清单上看到的敏感度与真正会被投递的内容**同源**，两处各写一个值迟早会出现"标着 public、搬的却是敏感数据"；
  - ⚠️ **`classification: secret` 的 topic 不派生点**：它本来就**禁止跨插件**（§1.12-2）⇒ 派生点等于承诺一条永远走不通的路（判定时 `UNKNOWN_POINT`，fail-closed）；
  - ⚠️ **2026-09-23 从 `install` 改成 `explicit`**（原口径"安装清单即生效、可一键收回"作废）：`install` 的真相是**清单里写一行就通**，而插件之间是**默认隔离**的（`exports` 默认私有、看不见别的插件）—— 监听别人的事件是**跨过去**，必须管理员**逐条**点头。改了之后"逐 topic 收回"也随之变成现成动作（撤的就是订阅方记录里的那条授权，见 §4.2-2）；  - 撤回只影响**后续投递**（正在跑的链不受影响，靠快照）；且**对运行中的插件要 reload 才生效**（装载时快照，见 api-contract §12-6）。

### 1.11 审计

- **`eventId` 贯穿一次发布/征询的所有投递**（这是"一次事件"的追踪主键，今天审计条目之间没有关联键）；
- 每次投递**一条**：`pluginId`（收件人）、`topic`、`eventId`、第几跳、耗时、结果（`opinion` / `skipped:<原因>`）、意见的 `decision`/`reason` 摘要；
- 发布方那一条记：`topic`、`bytes`（已有）、是否征询、收件人数、缺席数；
- 于是"**某插件反复拒绝**"是可追的：按 `pluginId` 筛、按 `topic` 聚合即可看出模式 ⇒ 管理动作：**逐 topic 撤销订阅** / 禁用 / 卸载。

### 1.12 §8.5 的第二跳封堵（保留，理由不变）

泄漏方可以是**发布方自己**（A 读到敏感数据 → 自己发布出去 → B 有出网），跟"核心广播不广播"无关。所以 `intent-capture.md` §8.5 的两条封堵照旧：

1. 授出网类权限时，**同屏列出该插件订阅的 topic 清单**；
2. `classification: secret` 的 topic **禁止跨插件**。

### 1.13 错误码（只增不改）

| 码 | 何时 |
|---|---|
| `EVENT_TOPIC_NOT_DECLARED` | **已有**：发布/订阅/绑定一个没在清单声明的 topic |
| `EVENT_ASK_NOT_SUPPORTED` | **新增**：对没声明 `ask` 的 topic 调 `request` |
| `EVENT_PAYLOAD_NOT_SERIALIZABLE` | **新增**：payload 里有不能 JSON 化的值 |
| `EVENT_PAYLOAD_TOO_LARGE` | **新增**：JSON 或字节部分超上限 |

装载期复用已有码：**订阅他人事件但没声明依赖** → `PLUGIN_EXPORT_INVALID`（`params` 说明是订阅声明问题）；**抢注 `core.` 前缀** → 同上。
按 `api-contract.md` §2 的规矩，新增码要同步补 `locales/zh-CN.json` 的 `err.<code>`。

### 1.14 明确不做（P2）

- **核心不发任何流程事件**：`exec.*` / `job.*` / `process.*` / `auth.*` 一律不做。exec/job/process 是**插件自己的动作**，结果它自己拿得到（任务句柄、返回值），别人没有知情权；`auth.*` 属于 §2；
- **不做广播**：投递只给声明过关系（清单 + 依赖 + 管理员批准）的插件，且**引用一律写完整引用**（§3.2）；
- **不止于此**：插件间"**要结果**"的需求走 §3 的**调用面**（点对点、拉），不要用事件凑；
- **不做跨插件强制裁决**：核心只搬运意见（§1.5）；
- **不做无界订阅**（异步迭代器形态）：那需要"无界阶段"，与既有阶段预算冲突（与 `fs.promises.watch` 同一个理由）。

### 1.15 验收口径（用例清单）

1. 没声明就发布 → `EVENT_TOPIC_NOT_DECLARED`（已有用例，保持）；
2. 订阅他人事件但没声明依赖 → 装载期 `PLUGIN_EXPORT_INVALID`；
3. 抢注 `core.` 前缀 → 装载期 `PLUGIN_EXPORT_INVALID`；
4. 管理员撤销订阅后：后续投递被跳过，审计记 `skipped: revoked`；正在跑的链不受影响；
5. **通知**：发布方 `publish` 立即返回（不因订阅方慢而变慢）；
6. **征询**：两个订阅方都收到，`opinions` 次序 = 管理员排的顺序；
7. **缺席**：让一个订阅方挂住 → 发布方拿到 `skipped: timeout`，而**不是** allow/deny；
8. **忙**：订阅方正跑定时器 → `skipped: busy`，链继续；
9. payload 带函数 → `EVENT_PAYLOAD_NOT_SERIALIZABLE`（宿主与沙箱两侧一致）；
10. payload 超上限 → `EVENT_PAYLOAD_TOO_LARGE`；
11. 二进制槽：JSON 主干 + 字节槽，两侧字节逐一致；
12. 一次征询的 N 次投递**共享同一个 `eventId`**；
13. `events.on` 绑一个没申报的 topic → 报错；绑定本身进运行时钩子表（审计可见）；
14. 处理函数里 `events.off()` → 本次链不受影响（快照）；
15. 卸载订阅方 → 运行时钩子表清空，不再收到投递。

## 2. 钩子链（结论保留，P2 不做）

### 2.1 定义与归属

**`hook` 类型 = 核心在流程的决策点上回调插件，且它的答复进核心决策**（中间件）。与另外三类的关系：

| 类型 | 调用方向 | 结构角色 |
|---|---|---|
| `ability` | **插件调核心**（`@host/api`） | 库：核心不知道它内部干什么 |
| `driver` | 插件调**它注册的端点** | 库（核心端特权版）：它提供领域能力给沙箱 |
| **`hook`** | **核心调插件** | **中间件**：插在核心流程里 |
| `theme` | 不跑代码 | 资源包 |

⇒ **裁决链属于 hook / driver，不外借给沙箱里的能力插件**。把 Linux 内核那套"通知链 + 安全模块钩子"用在互相隔离的第三方之间，是**把同信任域的机制搬到了隔离域**——这两件事必须分开（§1 / §3 与 §2 分节就是为了这个）。

**答复的形状**（原先草拟在 api-contract §3.2，随本节移过来；裁决链串行 + 链式修改 = 后一位看到前一位改过的数据）：

```ts
interface EventResult {
  status: 'allow' | 'deny' | 'modify' | 'pass';  // 放行 / 拦下 / 改了继续 / 我不管
  data?: unknown;     // modify 时的改写内容
  reason?: string;    // deny 时的原因（进审计）
  stop?: boolean;     // 「我放行，但后面不用问了」——照 Linux 的 NOTIFY_STOP
}
```

**P2 不做**，但结论保留，供 hook 轮直接使用。

### 2.2 从 Linux 学来的七条

| 做法 | 出处（Linux 6.12.110，行号基准见 `AGENTS.md` §3.1） | 对我们的含义 |
|---|---|---|
| **返回值协议**：不关心 / 赞成 / 别再往下叫 / 否决 / 赞成且收工；errno 能塞进返回值 | `include/linux/notifier.h:185-209` 的 `NOTIFY_*` 与 `notifier_from_errno` | 四态（放行/拦下/改了继续/我不管）够用；**要补一个"我放行，但后面不用问了"** |
| **顺序**：注册时按 `priority` **降序插入**；同一回调重复注册报错；同优先级可拒绝注册 | `kernel/notifier.c:25-45` 的 `notifier_chain_register` | 顺序用**显式优先级**，不靠猜。⚠️ 优先级**不能由插件自己写**（人人抢最高）⇒ **管理员在 Web UI 排** |
| **无限调用防护**：调用链用剩余次数封顶，并处理"回调里又注册了新回调" | `kernel/notifier.c:73-104` 的 `notifier_call_chain` | 我们跨 VM 风险更大 ⇒ 要**深度/次数上限 + 环检测**，超限 fail-closed |
| **两类链**：一类回调**不许阻塞**，一类**允许阻塞**；注册/注销还有上下文限制，且**注销不可以在调用链里做** | `include/linux/notifier.h:18-47`（原子链 / 阻塞链 / 原始链 / SRCU 链） | 钩子点分两类：**可裁决的**（必须能等，只能放在"进程上下文"式的点：登录、命令派发前）与**只通知的**（不许等：状态变化、装载卸载）。"处理中不许改登记"照抄 |
| **合成的粘性**：从默认值起，**第一个非默认返回值就短路**（后面的模块没有机会推翻前面的拒绝） | `security/security.c:994-1011` 的 `call_int_hook` | 可裁决链上：**先到的算数、后来者不能放宽**（fail-closed 方向） |
| **收件人与顺序在启动时定死**：顺序来自编译期内置序或启动参数，运行时只遍历这个静态定序且已启用的列表 | `security/security.c:1013-1016` 的 `lsm_for_each_hook`（顺序由 `ordered_lsms` 定） | 对应我们的"**清单声明 + 管理员批准 + 装载期定序**"，运行时只查表按序叫，**不接受运行时插队** |
| **阻塞式裁决的代价有先例**：fanotify 的权限事件让**发起方阻塞**等 listener 答复；另有"队列溢出"事件，溢出时权限事件只能拒绝 | `include/linux/fanotify.h:108-127` 的 `FAN_*_PERM` / `FAN_ALLOW` / `FAN_DENY` / `FAN_Q_OVERFLOW` | 每个裁决点都要有**等待预算 + 并发上限**，超时/溢出**一律 fail-closed（拦下）** |

### 2.3 等待与预算（跨 VM 的部分）

**两种发起方，性质不同**：

- **核心发起**（登录裁决）：核心在 Node 的 `await` 上等 ⇒ **暂停的是这一条流程，不是整个核心**（事件循环照常跑）；
- **插件发起**（A 征询 B 的意见）：A 挂在它自己那次宿主调用上 ⇒ 宿主去问 B、C 时它们都是空闲的。

**两种都不需要重入。** 唯一需要重入的情况是"**核心发起，而裁决方正是引发这次流程的那个插件**"（A 调 `exec.run`，而 `exec.before` 的名单里有 A）——**不支持**：该方本次**弃权** + 审计（`PLUGIN_BUSY` 是明确错误，不是死锁；不能定成"拒绝"，否则插件自己调一次就永久拒绝自己）。

**结论表**（P2 之后落地时照此实现）：

| 情况 | 处理 |
|---|---|
| 裁决方正忙 | **弃权 + 审计**（连续多次要告警） |
| 环形等待（A→B→A） | 因串行契约表现为明确的 `PLUGIN_BUSY`，**不是挂死**；链遍历用快照 |
| 预算 | **每方预算 + 整条链总预算叠加**，先到者算；等待**不耗 CPU**（挂起契约）但耗墙钟 |
| 超时 / 崩溃 | **视为拒绝**（fail-closed） |
| 处理期间被卸载 | **弃权 + 审计**（卸载是管理员的明确动作，不该顺带拒绝所有待裁决） |
| 链走一半被拒绝 | 发一条**回滚/事后通知**给已经答过的人（照 `kernel/notifier.c:122-129` 的 `notifier_call_chain_robust`）；配套纪律：**裁决方不要在 before 阶段做副作用** |
| 并行 | **可裁决链必须串行**（链式修改，顺序变结果就变）；**只通知链可以并行**；P2 之后第一版都串行 |

### 2.4 典型场景

**SSO 登录裁决**：插件在 `auth.login.before` 上注册裁决 → 核心在处理登录时按管理员排的顺序逐个回调 → 插件可以拦下、可以要求补一步（MFA）、可以放行 → **答复进核心决策**。

### 2.5 P2 期间核心唯一的"核心 → 插件"调用

不是事件、不进总线，方向相反：**依赖变更通知**。

- 时机：装载完成 / 卸载 / 重载 / 崩溃 / 禁用启用；
- 收件人：**声明依赖"出事那个插件"的插件**（不是"订阅"——可见性由依赖决定）；
- 内容：那个插件的状态与原因；**单向、不可裁决**；
- 埋点现成：`core/plugin/manager.ts` 的状态跃迁集中在一处，而"谁依赖谁"的查询也已经有了（现用于"被依赖时不许卸载/禁用"的反向保护）；
- 它顺手解掉 `plugin-lifecycle-design.md` 里挂着的两个待补项：**运行时依赖失效通知**、`OnPluginLoadedEvent`。

### 3.2 身份：`(origin, id)`，引用一律用完整引用

- **唯一性只能来自外部锚**：`id` 与 `author.id` **都是自述名字**（同名不同物是可能的）⇒ 身份 = **`(origin, id)`**（`plugin-signature-design.md` 的既有模型，实现要向它靠）；
- **本地来源也要具名**：`origin: null` 是个**坍缩的键** —— 所有本地安装都落在同一个 `local` 上，两个不同的人做同名插件必然相撞 ⇒ 本地来源写成 **`local:<名字>`**（保留前缀；默认 `local:default`；按人 / 按机器 / 按项目各建一个，管理员命名）。它**不是市场**：不可 fetch、没有公钥、不参与市场验签、**不提供更新渠道**；
- **同 `id` 不同 `origin` = 两个插件**（目录 / 配置 / 授权各自独立）；**同 `(origin, id)` 才谈升级**；
- **同一 `(origin, id)` 内、作者公钥不同 ⇒ 拒装**（`PLUGIN_AUTHOR_MISMATCH`）：机器分不清"作者换了钥"还是"另一个人"，必须管理员裁决（显式**接受换钥** / 换个源 / 先卸载）。**判据始终是公钥**，不是 `author.id` —— 名字谁都能写，这正是"看起来同作者"的包能被识破的地方；
- **完整引用** `<origin>/@user/name` 用于所有跨插件引用：**调用目标 / topic / 端点 path / 依赖声明 / 权限点名**；
- **作者公钥不进主键**：指纹不透明、换钥即换身份、还会外溢到目录名与命令行 —— 它只做**跨源同一性证明**（§3.6）。

### 3.3 "记源"要一路记到存储

| 位置 | 今天 | 改成 |
|---|---|---|
| 安装记录 | 主键 `id`（`findRecord` / `upsertRecord`） | 主键 **`(origin, id)`**；`install()` 加**来源入参** |
| 数据目录 | `data/plugins/xfy2412__hello` | `data/plugins/<sanitize(origin)>/xfy2412__hello`（`local:dev-a` → `local_dev-a`，`:` 不能进目录名） |
| 配置 | `config/plugins/xfy2412__hello.json` | `config/plugins/<sanitize(origin)>/xfy2412__hello.json` |
| 授权 | `PluginRecord.grants`，点名不含源 | 仍在记录里 ⇒ 天然按 `(origin, id)` 分开；**点名带源**（§3.4） |
| 能力登记 | `route:` / `api:` / `event:` 用裸 id | **带完整引用**（否则两个同名插件的路由与 path 撞车） |

- **存量迁移不做**（还没发布）：老目录按 `<sanitize(origin)>/` 规则重建即可。

### 3.4 权限点名带源

```
plugins.call.<origin>/@user/name.<path>
events.subscribe.<origin>/@user/name.<event>
本地来源：  plugins.call.local:dev-a/@user/name.<path>
```

- "**引用 → 权限点名**"的规范化函数 = `core/permissions/points.ts` 的 `callPointOf` / `subscribePointOf`（**✅ 已落地**，形状照 `core/exec/templates.ts` 的 `permissionPointOf` —— 那是现成先例）；
- **不转义、不摘要，就是字面拼接**，因为唯一性因此**可证**：origin 不含 `/` 与 `@`，id 恰好一个 `/` 与一个 `@`、名字段不含 `.` ⇒ 引用部分到**第一个 `.`** 为止，切分唯一。副产品是管理员在 CLI / 面板上看到的点名里**直接含插件引用**，可 grep、可与授权记录对照；
- **不反向解析**：展示层用**源别名 + 插件短名**，**存储与判定用全称**（别名可改 ⇒ 一旦进点名，改别名就会让授权凭空丢失）。撤销也不解析 —— 判定链只查"这个点名现在存不存在"（冻结表 ∪ 临时表，见 api-contract §6.0），授权存在**调用方记录**里，两边都不需要从名字里切回 `(ref, path)`；
- **点名必须"可声明"**，否则核心会登记一个**谁都申请不了**的点（管理员还能给它授权，却没有任何清单能声明它）。两条下限：
  - 尾段（`path` / `event`）**不含空白**（`permissions[].name` 的 schema 表达不了）——**不满足即装载失败** `PERMISSION_POINT_INVALID`，全有或全无，不留半登记；
  - 尾段**不含 `*`**（会被 `matchDeclaration` 当通配 ⇒ 一次声明就把对方**将来新增**的端点/订阅全预授权了，而 §3.7 要的是**增量同意**）；
  - ⚠️ **代价**：`permissions[].name` 的 schema 因此从"只有静态形状"放宽成**两条分支**（静态 `<group>.<action>[.<scope>]` + 动态 `<前缀>.<完整引用>.<尾段>`）。这是**接受更多输入**（只增不改），不是改既有规则；
- **点跟着能力生灭**（`core/permissions/source.ts` + `core/plugin/capabilities.ts`）：被调方/发布方登记能力时**派生**出点，`revoke` 时随登记一起消失（**临时表**，见 api-contract §6.0/§6.1 —— 冻结的注册表运行期不被插件改动）。**判定链查的是两张表的并集**；
- ⚠️ **ADR-001 v3 的"来源不参与权限判定"仍然成立**：来源出现在**引用**里 ≠ 来源参与**判定** —— 判定仍然只看"你有没有这个点"，同源与无源平等。将来若有人照 v3 的字面把 origin 从点名里删掉，会让两个同名插件无法区分；
- **爆炸半径很小**：只有"每个目标一条"的动态点带源；`events.publish` 这类基础点、`exec.template.*`（核心模板）、driver 注册的点（`db.query`）都**不受影响**；
- **仍未做**：无（**随能力生灭**与**管理员逐条撤回**两半都已通）。撤回 = 把点移出调用方记录的 `grants`（`explicit` 档，判定链第 3 步），另有 `plugin.revoke` 审计留痕 —— 见 §4.2-2。

### 3.5 依赖身份与作者签名

```json
"dependencies": { "plugins": [
  { "origin": "market.spc.xfyweb.cn", "id": "@b/backup", "version": ">=1.2.0 <2",
    "author": { "pub": "<base64 裸公钥>", "fingerprint": "sha256:…" } }
]}
```

**两个签名分工不同，不要混**：

| 签名 | 回答什么问题 | 归属 |
|---|---|---|
| **市场签名** | "这包是从我信任的那个市场来的吗、能不能静默更新" | **更新渠道**（keyring / 源） |
| **作者签名** | "**这是不是我依赖的那个插件**" | **依赖身份匹配** |

**作者签名 = 与市场签名同对象的全包签名**（2026-09-22 升级；原先写的"只签三元组"作废）：

- ⚠️ **为什么不签三元组**：只签 `(id, author.id, version)` 的签名**可以整段复制** —— 攻击者把这几个值连同签名原样搬进自己的包就验过了。它不绑定任何东西，连"连续性"都保不住；
- 所以作者签名签的对象与市场签名**完全相同**：`plugin.meta.json` 的规范化字节（它已经覆盖 manifest + 全部载荷即 `files[]`，等于签全包）。**零新增被签对象、零新增规范化规则**；
- 交付单元因此是**三个信封文件**（其余文件仍必须逐项出现在 `files[]` 里）：

```
plugin.meta.json     被签对象（新增字段 authorPub）
plugin.meta.sig      市场签名 —— 由**市场侧代码**产出（本地签不了，也不该签）
plugin.author.sig    作者签名 —— 由**构建工具**产出，用 authorPub 验，签的还是上面那份 meta
```

- ⚠️ **两个签名文件都不进 `files[]`**：作者签名要签 meta，而 meta 若列出"包含该签名的那个文件"，就形成「签名 → meta → 文件哈希 → 签名」的**循环**。（这也解释了现有信封为什么"不进 `files[]`"。）
- ⚠️ **验证永远用"期望的公钥"**：依赖声明里的 `author.pub`，或者作者名册里的首见值 —— **绝不用包里自述的 `authorPub`**，否则又回到自签自证；
- **它买到什么**：**完整性**（换一个字节就验不过）+ **连续性**（同一作者的后续版本仍由同一密钥签）；**买不到"这个作者到底是谁"**——那是市场或管理员锚定的事。有源包的身份由**市场命名空间间接背书**（`author.id = user@origin`，见 `core/sources/verify.ts` 的 `AUTHOR_MISMATCH`），本地包只有 TOFU；
- **它依旧不是信任锚**，但现在**真的能识别**了（原先那版不能）；
- 验签**复用** `core/sources/keys.ts` 的 `ed25519Verify` / `fingerprintOf` / `assertFingerprint` —— **零新密码学代码**。

**元数据由构建工具产出，市场审核完追加一个签名文件即可**：

| 谁 | 干什么 |
|---|---|
| **构建工具** | 算 `files[]` → 写 `plugin.meta.json`（含 `authorPub`）→ 用作者私钥签它 → 出 `plugin.author.sig` → 打包（**私钥永不进包**，包内也不含证书链） |
| **市场** | 审核 → 对**同一份字节**追加 `plugin.meta.sig`（**不改字节**，两把签名因此是**平级**的） |

- **市场的义务**（写进文档）：追加签名前核对 `files[]` 与实际载荷一致、核对它要背书的事实（如 `releasedAt`）；**不认可就拒签，不改写** —— 改写会破坏作者签名；
- 客户端仍然**逐文件核哈希** ⇒ 即使市场疏漏，端到端链路依然成立（市场签名 → meta → 每个文件哈希 → 载荷）；
- "**平台构建 / 自行构建**"两种来源因此走**同一套 meta 格式**：自行构建的包就是没有 `plugin.meta.sig` 的无源包（unanchored）；
- **`spc keygen` + `spc build --key` 只产作者签名**（市场签名是市场代码的事）。

**依赖声明**（形状：2026-09-24 加 `as` / `call`）与解析四步：

```json
"dependencies": { "plugins": [
  { "as": "backup", "id": "@b/backup", "origin": "market.spc.xfyweb.cn", "version": ">=1.2.0 <2",
    "author": { "pub": "<base64 裸公钥>", "fingerprint": "sha256:…" },
    "call": ["/api/backup/run"] }
]}
```

| 字段 | 必填 | 作用 |
|---|---|---|
| `id` | ✔ | 插件 id（`@user/name`）——**包内唯一**：同一清单里出现两次就必须给每条写 `as` |
| `as` | ✘ | **包内别名**：调用句柄（代码里 `plugins.call('backup', …)`）。只在包内有效、与源无关 |
| `author.pub` | ✔ | 同一性证明（见下） |
| `origin` | 按目标 | 市场目标必填；本地目标省略（见下面的四格表） |
| `version` | ✘ | 版本区间（解析待 P2） |
| `call` | ✘ | **调用面的请求**：我要调它的哪些端点（`path` 列表）。声明跟着依赖走 ⇒ **包内不带源**；授权仍落在带源的实际点位上 |

- **`author.pub` 是必填**（2026-09-24 定）：构建层**强制签名**（不存在无签名包），而 `id` 与 `author.id` **都不唯一** ⇒ 唯一性来自 `origin`、**同一性来自公钥**，两者缺一不可。`origin` 的写法按目标分四格（下表）。
- `fingerprint` 可选，写了就**必须与 `pub` 自洽**（照 `core/sources/keyring.ts` 的 `assertFingerprint` 先例）；
- **解析比公钥、不比指纹字符串**（指纹只在展示/审计里用）：这是**功能正确性**问题 —— 比错了会把 A 接到错的 B 上；
- 宿主侧另存一张**作者名册** `(origin, id) → { pub, fingerprint, firstSeenAt }`：连续性 + 展示 + 审计（不是信任锚，只是"这个名字以前是谁"）。它与 `keyring` 的源条目**共用机制、分开存储**：源由**管理员**锚定、永不自动新增；作者**首见即记**（是识别，不是信任）；
- 解析四步：① 读 A 的声明取 `author.pub`（+ 可选指纹自洽）→ ② 读已装 B 的 `plugin.meta.json` + `plugin.author.sig`，**用 A 声明的公钥**验签 → ③ 公钥不等或验签失败 ⇒ **依赖不满足** → ④ 比版本区间与 `origin`。

#### `origin` 的写法按**目标**分四格（2026-09-24 定）

| 声明者 → 目标 | 写法 | 为什么 |
|---|---|---|
| 任意 → **市场包** | `origin` **必填**（市场域名） | 市场域名是**作者发布时就知道**的稳定标识；同名插件在两个市场就是两个不同的东西 |
| 本地包 → **本地包**、**省略 `origin`** | **在"本地源范围"内**按 `author.pub + id` **唯一匹配**（0 个 ⇒ 不满足；2 个 ⇒ 歧义拒） | ⚠️ **桶名是"装机的人"起的标签**（`std（小A）`），作者签名时**不可能知道它** ⇒ 写死桶名的声明**本来就不自足**。同桶的情形天然继续工作（唯一匹配就命中它自己那个桶），于是 **[promote 搬运](#36-换源reanchor) 不会打断本地→本地的依赖** |
| 本地包 → 本地包、**写明 `local:<名字>`** | 精确匹配该桶（照旧） | 作者自愿承担"对不上"的风险 |
| **市场包 → 本地包** | **禁止**（构建期 / 装载期拒） | 本地源**不存在于别人的机器上**，这种声明在任何别的机器上都不可能满足 |

> 同源简写的原口径（"省略 = 取依赖方自己的来源"）在**市场包之间**不变；上表第 2 行是**本地目标**的扩展 —— 因为对本地包，唯一性实际来自**作者公钥**（`plugin-signature-design.md` §3bis 的"本地源 = 一个作者的桶"）。⏳ **未落地**，随 ④ 一起做。

### 3.6 换源（reanchor）

| 情形 | 判定 | 数据 / 配置 / 授权 |
|---|---|---|
| 同 `(origin, id)`、版本递增 | 升级 | 保留 |
| 同 `id` 不同 `origin`、**公钥相同** | **同一个插件** ⇒ 走 reanchor | **迁移过去**（显式动作，不静默） |
| 同 `id` 不同 `origin`、公钥不同 | **两个插件** | 各自独立 |
| 同 `(origin, id)` 但公钥变了 | 作者换钥 ⇒ 告警 + 需显式接受 | 保留 |

**分不分家由主键定，能不能搬家由公钥证。**

**搬运会动到什么 —— 按"谁指向它 / 谁修得了"分类**（2026-09-24 补，这是搬运设计的判据）：

| 谁指向被搬的插件 | 存在哪 | 搬运之后 | 宿主能单方面修吗 |
|---|---|---|---|
| 它自己的数据 / 配置 / 授权 | 自己那条记录 + 磁盘目录 | 一起搬 | ✅ 能 |
| **别人对它的跨插件授权**（点是它提供的） | **别人的记录**（宿主侧） | 点名随源变 ⇒ 旧授权挂空（`UNKNOWN_POINT`） | ✅ **能**：点名是**生成**出来的，用「旧点名集合 → 新点名集合」映射重写别人的 `grants`（不解析点名，只做字符串替换） |
| **别人的依赖声明**（`{ origin, id, author }`） | **别人的包里 —— 被签名的字节** | 依赖不满足 ⇒ 依赖方**装载失败** | ❌ **不能**（改一个字节就破签名） |
| 审计历史里的 `ref` | 审计日志 | 只是历史，正确 | 不适用 |

⇒ 三条硬要求：① **批量原子**（同一个作者的几个一起搬；否则出现"依赖方在新桶、被依赖方在旧桶"的中间态）；
② **被依赖的插件不许单独搬**（`PLUGIN_IN_USE` 的语义扩展："换个源"也是"抽走" —— 要么连依赖方一起搬，要么先处理依赖方）；
③ 搬运是**跨记录**操作，必须过 manager 唯一锁 + 落审计（旧/新 origin、公钥指纹、点名映射、会被打断的依赖方清单）。
而[上表](#origin-的写法按目标分四格2026-09-24-定)第 2 行那条规则（本地目标省略 `origin` ⇒ 本地范围唯一匹配）正是"本地→本地的依赖不会因为 promote 而断"的原因。

**本地侧的典型搬运 = promote**（`plugin-signature-design.md` §3bis）：同一个作者在杂桶里出现第二例时，建一个属于他的源并把这一组搬过去；因为公钥相同，reanchor 的前提天然满足。

```
动作：spc plugin reanchor <完整引用> --origin <新来源>        （面板入口属 P3）
前提：新包的作者公钥 == 记录里的 authorFingerprint
做：  改 origin / signedBy / verifiedMeta
      + 搬数据目录（<sanitize(旧 origin)>/ → <sanitize(新 origin)>/）
      + 重写记录里的 grants 与 capabilities（§3.4 的点名随源变）
      + **重写所有引用它的记录的 grants**（旧点名集合 → 新点名集合，字符串替换）
      + 审计 plugin.reanchor（旧/新 origin、指纹、新旧点名映射、被牵连的记录）
⛔ 前置检查：被别的已启用插件**依赖**时不许单独搬（PLUGIN_IN_USE 的扩展）——
   要么把同一作者的那几个**一起原子搬**，要么先处理依赖方
```

**典型场景正是"先本地发放、后上市场"**：`local:dev-a/@a/foo` → `market.spc.xfyweb.cn/@a/foo`（公钥一致即可换源，数据 / 配置 / 授权一起搬过去）。本地源之间也允许（`local:dev-a` → `local:dev-b`，比如按机器重新归属，或者 §3bis 的 **promote**：为某个作者单独建源）。

**必须提示管理员**：`unanchored → anchored` 意味着该插件**从此可静默升级**（一次实质的信任升级）；反向（市场 → 本地）同样允许，之后失去更新渠道。

⚠️ 与 §3.2 的分工：**同 `(origin, id)` 内公钥不同是"拒装"**（不是 reanchor）—— 那是"这个插件换人了"，必须管理员显式接受换钥、换源或先卸载。reanchor 只处理"**公钥相同、来源不同**"。

### 3.7 调用方法、门槛与失败语义

沙箱内：`plugins.call(<依赖句柄>, path, paramsJson, bytes?)` → **JSON 文本**（照 `exec.run` 的约定：唯一不自动解码的方法）+ 可选字节槽（与事件面同一条通道）。

⚠️ **第一个参数不是"完整引用"，是清单里那条依赖的句柄**（2026-09-24 定）：

- 句柄 = 依赖条目的 **`as`**（包内别名）；没写 `as` 时用 **`id`**。**同一清单里 `id` 必须唯一；重名就必须给每条依赖写 `as`** —— 歧义在**清单校验期**就挡掉，所以代码里永远无歧义，单依赖的常见情形也不用多写一行；
- **为什么不让代码写源**：本地源的名字是**"装机的人"起的标签**（`std（小A）`，promote 后成 `local:std-a`），作者签名时**不可能知道**它；写进代码就等于"换一次桶，所有调用方全部重建"；
- ⇒ **包内被签名的字节里不存在本地源名**（只有依赖市场包时才写市场域名，而它天然稳定）；promote / 本地源改名**不需要任何插件重建**。

**锚定解析（宿主侧，装载时一次）**：

```
句柄 → 清单里那条 dependencies.plugins[] 声明 → 按 (origin?, author.pub, id) 解析成**实际 ref**
     ⇒ 生成具体点名 plugins.call.<实际 ref>.<path>
判定 / 授权 / 临时表 全部按**带源的点名**走（管理员批准的是"这个具体的插件"）；
审计条目与响应信封记**实际 ref**（origin / id / version）—— 源出现在该出现的地方
```

**四条门槛**（与事件面同构）：

1. 调用方在 `dependencies.plugins` 里**声明依赖它**（句柄只在声明的范围内有效 —— "看不见别的插件"是默认）；
2. **`path` 在该依赖条目的 `call` 列表里**：**"我要用它什么"是包内被签名的请求**，替代了 `permissions[]` 里那条带源的动态点名（声明不带源、**授权带源**）；
3. 被调方的端点声明 `callable` 含 `'plugins'`；
4. 管理员在动态点 `plugins.call.<实际引用>.<path>` 上授予（`scope: host`、**`grant: explicit`**）—— ⚠️ **2026-09-23 从 `install` 改成 `explicit`**：`install` 等于"清单里写一行就通"，而插件之间默认隔离，跨过去必须逐条点头。

**候选集随被调方升级重算**：它删掉的端点自动失去授予（fail-closed），新增的端点走**增量同意**。
**被调方换源（promote / reanchor）后**：句柄不变、`call` 不变、宿主重新解析；**只有管理员的授权要跟着重写**（点名随源变，§3.6）—— 这是搬运唯一需要宿主动手的地方。

**失败语义**：

| 情况 | 处理 |
|---|---|
| 对方忙（`PLUGIN_BUSY`） | **有界重试**：宿主侧最多 3 次尝试、间隔 50 / 100 / 200 ms、总计 ≤ 350 ms，**计入调用方自己的阶段预算**；审计记 `attempts` + `waitedMs` |
| 对方崩溃 / 已卸载 / 被禁用 | **不重试**（重试崩溃＝反复去叫一个坏掉的插件）⇒ 调用失败 |
| 超时 | 调用失败，**绝不返回部分结果**（fail-closed） |
| 一律不做 | **不排队**：顺序等到对方空闲会让调用方预算被对方吃掉，而且"谁先谁后"变得不可解释 |

**重入与死锁**（结论与 §2.3 同源）：调用方 A 挂在**自己那次宿主调用**上 ⇒ **不需要重入**；宿主进 B 的 VM 时 B 必须空闲；**A→B→A 回环**在第二次进 A 时因 A 正忙而**快速失败**（串行契约白送，不是死锁）；再加**嵌套深度上限**；被调方处理器里**不能改自己的登记**（快照）。

**返回值与错误**：成功 = JSON 文本（+ 可选字节槽）；失败 = 结构化错误码（被调方自己的 `code`/`params` 原样回传），**被调方的堆栈与内部细节只进审计、不给调用方**；响应信封带 `callee: { origin, id, version }`（P2 不做 API 版本目录 —— 只给这一个事实 + 依赖声明里的版本区间）。

**审计**：一条 `plugins.call`（caller / callee / path / bytes / duration / result）+ **`callId` 关联** —— 被调方内部因此产生的条目带同一个 `callId`，一次跨插件交互在审计里能串起来（与事件的 `eventId` 同构）。

### 3.8 与事件面的分工，与明确不做

**需要结果 → 调用（拉）；只想通知或征求意见 → 事件（推）。** 两者都要求"显式声明关系 + 管理员批准"，都不允许 A 偷偷碰 B。

**P2 明确不做**：

- 插件间的**长连接 / 事件流**（要推送就用事件面）；
- **跨核心调用**；
- **API 版本目录**（"查询某插件导出了哪些端点、各自什么版本与形状、并做多版本共存与协商"）—— 收益要等第三方生态，P2 只给"响应带 `callee.version` + 依赖里的版本区间"；
- 把端点暴露给"**任意插件**"（必须逐个 callee 声明依赖 —— 与 topic 枚举声明同一个取向）。

**面板那条路与这条路互不复用**：面板走核心网关 + frontend-token（还带 grantId / 意图确认，P3），插件走 `plugins.call` + 权限点；被调方的同一段实现两边都能用到，但**入口与鉴权分开**。

### 3.9 连带：依赖从"软可见"变成"硬依赖"

插件间调用让依赖变成**硬依赖**（B 不跑，A 那段功能就废）⇒ §2.5 的**依赖变更定向通知**从"顺手解掉的待补项"升级为**必需**（A 得能在 B 掉线时收到通知并降级）。

### 3.10 顺手必须修的现状缺陷（都在这一批）

1. `core/plugin/manager.ts` 的依赖检查**只比 id**（`.map(d => d.id)`）；
2. `sdk/types.ts` 的 `dependencies.plugins` **缺 `origin`**（schema 里有）；
3. `install()` **没有来源入参**，且遇到同 id 已装会**静默覆盖**（无作者校验、`origin` 也不会被市场接管）⇒ 按 §3.2 的规则改成"同 `(origin, id)` 覆盖 / 同 id 不同源 = 两个插件"，并加**防同名顶替**校验（比作者公钥）。

新码（只增不改）：`PLUGIN_AUTHOR_MISMATCH`（同 id 不同公钥）、reanchor 相关码；~~`kind: 'webApi'` 系列参数值~~ **✅ 已随改名改成 `'endpoint'` / `'endpoint-permission'`，能力标签也从 `api:` 改成 `endpoint:`**。

### 4.4 引用口径（四份冻结的帧，怎么引）

| 引谁 | 怎么写 | 帧 |
|---|---|---|
| **本仓库自己的源码** | **只写符号名**（如 `core/permissions/check.ts` 的 `effectiveLevel`），**不写行号** | 无（我们自己这份每次提交都在动） |
| 引擎 / Node 源码 / 第三方包 | `符号` + `文件:行号`，文件按各自树根写（`vendor/quickjs/quickjs.c`、`lib/fs.js`） | fork 提交 / Node 提交 / `pnpm-lock.yaml` |
