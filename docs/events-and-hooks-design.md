# 事件与钩子设计（events & hooks）

> **状态**：**§1 事件面 = P2 落地范围**；**§2 钩子链 = 结论保留、P2 不做**（等协作插件 `hook` 那一轮）。
> **依据**：ADR-001（零环境权力）、ADR-005（沙箱与插件类型）、`manifest-design.md` §6（插件间可见性）、
> `api-contract.md` §3/§6/§7、`intent-capture.md` §8.5（第二跳）。
> **取代关系**：本文重写 `api-contract.md` §3 的"事件总线"部分；其余文档的同步清单见 §3。

## 0. 一句话

沙箱里**没有"总线"**，只有**显式关系上的消息投递**：插件自己发布事实，声明过关系的插件收到；
**核心只搬运**——不广播、不解释、不裁决。

三条推论先摆在这里，后面所有条款都是它们的展开：

1. **"广播"不存在**：每一跳的收件人，在装载时就登记好了（清单声明 + 管理员批准）；
2. **核心不往里发东西**：插件调用了什么、核心做了什么，都不是事件；**发布永远是插件自己的动作**；
3. **核心不解释意见**：征询回来的意见**原样**交给发布方，采纳与否由发布方自己的代码决定。

## 1. 事件面（P2 做）

### 1.0 现状（2026-09-22 核对代码）

| 面 | 现状 |
|---|---|
| 清单形状 | ✅ `sdk/types.ts`：`exports.events.publish[]{topic, classification}` / `subscribe[]{topic, mode}` |
| 能力登记 | ✅ `core/plugin/capabilities.ts`：**一个 topic 只能有一个发布者**（第二个 owner → `PLUGIN_EXPORT_INVALID`）；登记 `published` / `subscriptions` 两张表；`capabilities` 记 `event:<topic>` / `subscribe:<topic>`；全有或全无、可精确撤销 |
| 发布 | ⚠️ **只有一半**：`core/hostApi.ts` 的 `events.publish` 校验 topic 在声明内（否则 `EVENT_TOPIC_NOT_DECLARED`），解码 payload、算字节数，返回 `{ ok, topic, bytes }` ——**payload 到宿主就停了**：没有订阅者、没有任何投递 |
| 订阅 | ❌ 不存在（只有登记） |
| 权限点 | ⚠️ 只有 `events.publish`（`scope: self` / `grant: auto`）；**订阅方向没有权限点** |

### 1.1 为什么不是"广播"

`manifest-design.md` §6 已经定了：**插件默认看不见其他插件；要订阅他人事件、或调用他人 Web API，必须在 `dependencies.plugins` 里显式声明**。
所以"核心把 A 的动作广播给所有订阅者"= 核心替 A 把它要干什么告诉了**没声明依赖 A 的第三方**，与那条规则直接冲突。
更根本的一点：插件之间是**声明过的、有向的关系**；插件与核心之间没有这层关系（所有插件都依赖核心）⇒ 核心发事件就是无差别广播。

Linux 在同一件事上的做法可以直接对照（下面几条都来自 Linux 6.12.110，见 §3 的引用口径）：

- **netlink / connector**：`cn_netlink_send_mult()` 只把消息投给**显式 join 过该组**的订阅者，而且"**没有听众**"是一等公民状态（返回 `-ESRCH`，不是异常流程）（`include/linux/connector.h:78-127`）；
- **inotify**：订阅方**自己声明 mask**（关心哪些事件位），每个观察者**自己的队列**，队列溢出本身就是一条事件（`IN_Q_OVERFLOW`）（`include/linux/inotify.h:12-18`）；
- 内核**从不对用户态广播"某个进程在干什么"**——根本没有这样的总线。

⇒ 我们要的形态就是这三条：**关系先显式建立、只投给声明过的人、每个订阅者独立可观测**。

### 1.2 命名空间与所有权

- **`core.` 是保留前缀**（核心将来要发的事实；P2 里核心不发任何事件）；插件只能用**自己的 id** 开头：`@publisher/name.<事件名>`。
  ⚠️ 这是**新增校验**：今天 `capabilities.ts` 只查"同 topic 的 owner 唯一"，插件完全可以抢注一个听起来像核心的 topic（如 `core.exec.before`）并成为它的 owner。要补保留前缀校验，违反 → `PLUGIN_EXPORT_INVALID`。
- **一个 topic 只能有一个发布者**（已有规则，保持）。订阅方数量不限。
- 事件名是**英文契约**（与错误码同规矩）：渲染层翻译，核心不做本地化。

### 1.3 两种用法：通知与征询

| 用法 | 调用 | 语义 | 核心做什么 |
|---|---|---|---|
| **通知** | `events.publish(topic, payload)` | "我做了/我要做这件事"，**不等任何人** | 查收件人 → 投递 → 记审计 |
| **征询** | `events.request(topic, payload)` → `{ eventId, opinions }` | "**我想听听你们的意见**" | 查收件人 → 按序逐个问 → **把意见原样装成列表交回** |

- **一个 topic 支不支持被征询，由发布方在清单里声明**：`publish[].ask?: boolean`（**新增字段**，缺省 `false`）。
  对没声明 `ask` 的 topic 调 `request` → `EVENT_ASK_NOT_SUPPORTED`。
- 订阅方的 `mode` 语义写准：`notify` = **只听**；`arbitrate` = **我愿意出意见**（不是"我裁决"）。
  两边不匹配**不报错**，只是永远收不到征询。
- **同一个 topic 可以既被通知式发布、也被征询式请求**——由发布方的代码决定这一次要哪种。

### 1.4 场景走一遍（数据库刷新 + 定时备份）

数据库插件 `@a/sqlite` 声明发布 `refresh-started` / `refresh-finished`，备份插件 `@b/backup` 声明订阅、并声明依赖 `@a/sqlite`。

**用法一：通知（推迟备份）**

1. `@a/sqlite`：`events.publish('@a/sqlite.refresh-started', { at })`，**说完就走**；
2. 核心查登记表 → 收件人只有 `@b/backup` → 投递给它（此刻它空闲）；
3. `@b/backup` 把"正在刷新"记在自己状态里；定时器到点时看到这个状态，**主动推迟**；
4. 收到 `refresh-finished` 后恢复备份。

这条路径**不需要任何裁决机制**——发布方只管说，订阅方自己决定怎么办。

**用法二：征询（拒绝现在刷新）**

1. `@a/sqlite`：`const r = events.request('@a/sqlite.refresh-started', { at })`；
2. 核心按**管理员排的顺序**逐个进订阅方的 VM 收意见；`@b/backup` 返回 `{ decision: 'deny', reason: 'backup in progress' }`；
3. 核心把意见装成列表交回；`@a/sqlite` 的代码看到 `deny`，**自己决定**是推迟刷新、还是照样刷；
4. 核心全程**不拦、不改、不替它下结论**。

**恶意反复拒绝**：审计里每一次投递都有记录（谁、哪个 topic、第几次、什么意见、耗时）⇒ 管理员据此**逐 topic 撤销它的订阅**，或者禁用/卸载（见 §1.11）。

### 1.5 "核心只搬运意见"消掉了四类问题

| 原本要设计的 | 为什么不用了 |
|---|---|
| 多个 `modify` 怎么合成（链式改写还是冲突即拒） | 核心**不解释**意见：每条意见独立、原样交回，由发布方自己合 |
| 拒绝的"粘性"（后面的人不能推翻前面的拒绝） | 同上——没有"核心裁决"这回事，就没有粘性可言 |
| `deny` 要不要短路后续裁决方 | **默认问完所有人**，把全部意见交回 |
| 核心流程被插件卡住 | 等待的是**发布方自己**（它挂在 `request` 那次宿主调用上），核心流程不参与 |

> 这四条连同 §2 的整套规则，**都属于"核心强制裁决"的世界**——那是 hook / driver 的事，P2 不做。

### 1.6 意见的形状，与"没答"

**SDK 约定**（核心不解释，但要求一个最小形状，否则审计与发布方都没法用）：

```
{ decision?: 'allow' | 'deny' | 'defer' | string, reason?: string, data?: unknown }
```

- 核心**只保证它是 JSON**、只把 `decision` / `reason` 写进审计，**不因它改变任何流程**；
- 处理函数**可以不返回**（= 没意见）；
- 处理函数可以返回 Promise（宿主会等它，受 §1.9 的预算约束）。

**核心交给发布方的结果**：

```
{ eventId, opinions: [
    { pluginId, outcome: 'opinion', data, reason, ms },
    { pluginId, outcome: 'skipped', skipReason: 'busy'|'timeout'|'crashed'|'unloaded'|'revoked' }
] }
```

**硬规矩：核心不许把"没答"塌缩成"同意"或"拒绝"。** 缺席就是缺席，四种原因分开报：
`busy`（`PLUGIN_BUSY`，按既定串行契约**弃权**）/ `timeout` / `crashed` / `unloaded`（处理期间被卸载，延后拆保证了拿得到状态）。
**怎么解读缺席，是发布方自己的逻辑**（SDK 文档里建议保守处理，但核心不强制——见 §0 第 3 条）。

### 1.7 收件人、顺序、门槛

**收件人**（三个条件全满足才投）：

1. 该插件在清单里**声明订阅**了这个 topic；
2. 该插件在 `dependencies.plugins` 里**声明依赖**发布方（`manifest-design.md` §6；缺失 → 装载期 `PLUGIN_EXPORT_INVALID`）；
3. 管理员**批准**了这条订阅，且**没有撤销**（§1.10）。

**顺序**：管理员在 **Web UI 手工排**，**按 topic 各排一张表**（同一个插件在不同 topic 上可以排不同位置）。

- 没排过 ⇒ 按**装载序**，UI 上显式标"未排序"；
- **快照生效**：排序变更**在下一次投递才生效**，不改动正在跑的链；
- 顺序决定**问的次序**与 `opinions` 列表的次序（P2 不短路，所以它不影响结果，只影响可读性与耗时）。

**门槛只剩"听"这一把**（"拦"那一把属于 §2）：

- 事件的等级由**发布方逐次声明**（"这一次有多敏感"），没声明就按**清单登记**的 `classification` 兜底；
- 合成沿用已有实现：`effective = max(订阅方声明, 管理员覆盖, 清单兜底)`，**只升不降**（`core/permissions/check.ts` 的 `effectiveLevel`）；
- ⚠️ **现状缺口**（`api-contract.md` §7.1 已记）：桥调用判定时**没把 `meta` / `userOverride` 传进去**，也没有 `pathLevels` 配置 ⇒ 今天等于"每个权限点一个固定等级"。本设计要接线：宿主原语声明"这次碰的是什么"（`metaFor`）+ 管理员覆盖真的存在 + 审计记合成后的真值。
- ⚠️ **不要在仿真层（`node-*.js`）里判等级**：等级属于"碰资源的那一层"，与 `scope`/`grant` 同源。

### 1.8 payload 与二进制

- **只能是 JSON 能表示的值**。显式拒绝（fail-closed，**不静默丢字段**）：函数、类实例、Symbol、循环引用、`Map`/`Set`/`Date`/`RegExp`、Promise ⇒ `EVENT_PAYLOAD_NOT_SERIALIZABLE`。
- **体积上限**：JSON 部分与字节部分**分开计量**，超限 ⇒ `EVENT_PAYLOAD_TOO_LARGE`。没有上限的话，事件就是绕过文件读写限额搬运大文件的后门（`bytes` 今天已经在算，正好复用）。
- **二进制走单独的槽**，不塞进 JSON（照抄仿真模块的做法：`fs.readBytes` / `bytes.*` 走的就是这条通道）：
  - 沙箱 → 宿主：宿主方法参数本来就允许字节（`HostArg = string | Uint8Array`）；
  - 宿主 → 沙箱：用 `newArrayBuffer` 造句柄（与 `binaryResult` 同一条路）；
  - 契约不变：**ArrayBuffer = 数据，字符串 = 错误**。
  ⚠️ **要动投递链**：现在"宿主叫插件"只传字符串（定时器、文件监视都是），要加字节槽。
- 不在 JSON 里塞 base64：膨胀 33%，还要求两端各实现一套约定。

### 1.9 投递机制（复用现成积木，不发明新通道）

| 用法 | 走哪条现成的路 |
|---|---|
| **通知** | `fs.watch` 那条：宿主排队 → 唤醒插件（`bridge.deliver` 加第三种 `kind: 'event'`）→ 插件来取（`take`）→ 审计 `beginPhase` |
| **征询** | 生命周期钩子那条：从模块命名空间按名字取导出、宿主直调、可返回 Promise、有 deadline、有 `PLUGIN_BUSY` 守卫（与 `callHook` 同形） |

**订阅面**：清单里**声明**（授权面）+ 运行时 `events.on(topic, handler)` **绑定处理函数**。

- 为什么两条都要：`plugin-lifecycle-design.md` §3 定过"**manifest 是审核对象与唯一事实源；插件说了不算**"——所以**能不能发/能不能听**必须走清单，运行时的 `events.on` **只能绑已申报的 topic**（否则 `EVENT_TOPIC_NOT_DECLARED`）；
- 这是插件作者习惯的写法（Velocity 那类也是手动注册；我们不做装饰器——插件是纯 ESM，没有转译步骤）；
- 核心为每个插件维护**运行时钩子表**（`events.on` 过桥时登记）：投递前知道"有没有听众"（没听众就不用叫醒插件）、审计能记"实际绑了什么"、征询时知道该等谁；**插件卸载时这张表随之清空**。
- **处理中不许改登记**：链在遍历开始时做**快照**，处理函数里 `events.off()` 只影响下一次（照抄 Linux 明文禁止的"在调用链里注销"）。

### 1.10 权限点与档位

- `events.publish`：**已有**，`scope: self` / `grant: auto`（发布自己的事，够不着别人，保持不动）。
- **订阅他人事件要新增权限点**（今天没有）：**动态权限点 `events.subscribe.<topic>`**（与 `exec.template.<id>` 同一套路：topic 里的 `:`/`.` 归一成权限点名的分隔符），`scope: host`、`grant: install`。
  - 落在 `install` 档的含义：**安装清单即生效、可一键收回、可逐 topic 收回**——正好是"管理员能禁止某插件监听某些事件"这条需求的最小落点；
  - 撤销只影响**后续投递**（正在跑的链不受影响，靠快照）；
  - ⚠️ 今天登记的 `subscribe:<topic>` 只是能力标签，**撤销粒度还没有**，要补。

### 1.11 审计

- **`eventId` 贯穿一次发布/征询的所有投递**（这是"一次事件"的追踪主键，今天审计条目之间没有关联键）；
- 每次投递**一条**：`pluginId`（收件人）、`topic`、`eventId`、第几跳、耗时、结果（`opinion` / `skipped:<原因>`）、意见的 `decision`/`reason` 摘要；
- 发布方那一条记：`topic`、`bytes`（已有）、是否征询、收件人数、缺席数；
- 于是"**某插件反复拒绝**"是可追的：按 `pluginId` 筛、按 `topic` 聚合即可看出模式 ⇒ 管理动作：**逐 topic 撤销订阅** / 禁用 / 卸载。

### 1.12 §8.5 的第二跳封堵（保留，理由不变）

泄漏方可以是**发布方自己**（A 读到敏感数据 → 自己发布出去 → B 有出网），跟"核心广播不广播"无关。所以 `intent-capture.md` §8.5 的两条封堵照旧：

1. 授出网类权限时，**同屏列出该插件订阅的 topic 清单**；
2. `classification: secret` 的 topic **禁止跨插件**。

### 1.13 错误码（只增不改）

| 码 | 何时 |
|---|---|
| `EVENT_TOPIC_NOT_DECLARED` | **已有**：发布/订阅/绑定一个没在清单声明的 topic |
| `EVENT_ASK_NOT_SUPPORTED` | **新增**：对没声明 `ask` 的 topic 调 `request` |
| `EVENT_PAYLOAD_NOT_SERIALIZABLE` | **新增**：payload 里有不能 JSON 化的值 |
| `EVENT_PAYLOAD_TOO_LARGE` | **新增**：JSON 或字节部分超上限 |

装载期复用已有码：**订阅他人事件但没声明依赖** → `PLUGIN_EXPORT_INVALID`（`params` 说明是订阅声明问题）；**抢注 `core.` 前缀** → 同上。
按 `api-contract.md` §2 的规矩，新增码要同步补 `locales/zh-CN.json` 的 `err.<code>`。

### 1.14 明确不做（P2）

- **核心不发任何流程事件**：`exec.*` / `job.*` / `process.*` / `auth.*` 一律不做。exec/job/process 是**插件自己的动作**，结果它自己拿得到（任务句柄、返回值），别人没有知情权；`auth.*` 属于 §2；
- **不做广播**：投递只给声明过关系（清单 + 依赖 + 管理员批准）的插件；
- **不做跨插件强制裁决**：核心只搬运意见（§1.5）；
- **不做无界订阅**（异步迭代器形态）：那需要"无界阶段"，与既有阶段预算冲突（与 `fs.promises.watch` 同一个理由）。

### 1.15 验收口径（用例清单）

1. 没声明就发布 → `EVENT_TOPIC_NOT_DECLARED`（已有用例，保持）；
2. 订阅他人事件但没声明依赖 → 装载期 `PLUGIN_EXPORT_INVALID`；
3. 抢注 `core.` 前缀 → 装载期 `PLUGIN_EXPORT_INVALID`；
4. 管理员撤销订阅后：后续投递被跳过，审计记 `skipped: revoked`；正在跑的链不受影响；
5. **通知**：发布方 `publish` 立即返回（不因订阅方慢而变慢）；
6. **征询**：两个订阅方都收到，`opinions` 次序 = 管理员排的顺序；
7. **缺席**：让一个订阅方挂住 → 发布方拿到 `skipped: timeout`，而**不是** allow/deny；
8. **忙**：订阅方正跑定时器 → `skipped: busy`，链继续；
9. payload 带函数 → `EVENT_PAYLOAD_NOT_SERIALIZABLE`（宿主与沙箱两侧一致）；
10. payload 超上限 → `EVENT_PAYLOAD_TOO_LARGE`；
11. 二进制槽：JSON 主干 + 字节槽，两侧字节逐一致；
12. 一次征询的 N 次投递**共享同一个 `eventId`**；
13. `events.on` 绑一个没申报的 topic → 报错；绑定本身进运行时钩子表（审计可见）；
14. 处理函数里 `events.off()` → 本次链不受影响（快照）；
15. 卸载订阅方 → 运行时钩子表清空，不再收到投递。

## 2. 钩子链（结论保留，P2 不做）

### 2.1 定义与归属

**`hook` 类型 = 核心在流程的决策点上回调插件，且它的答复进核心决策**（中间件）。与另外三类的关系：

| 类型 | 调用方向 | 结构角色 |
|---|---|---|
| `ability` | **插件调核心**（`@host/api`） | 库：核心不知道它内部干什么 |
| `driver` | 插件调**它注册的端点** | 库（核心端特权版）：它提供领域能力给沙箱 |
| **`hook`** | **核心调插件** | **中间件**：插在核心流程里 |
| `theme` | 不跑代码 | 资源包 |

⇒ **裁决链属于 hook / driver，不外借给沙箱里的能力插件**。把 Linux 内核那套"通知链 + 安全模块钩子"用在互相隔离的第三方之间，是**把同信任域的机制搬到了隔离域**——这两件事必须分开（§1 与 §2 分节就是为了这个）。

**答复的形状**（原先草拟在 api-contract §3.2，随本节移过来；裁决链串行 + 链式修改 = 后一位看到前一位改过的数据）：

```ts
interface EventResult {
  status: 'allow' | 'deny' | 'modify' | 'pass';  // 放行 / 拦下 / 改了继续 / 我不管
  data?: unknown;     // modify 时的改写内容
  reason?: string;    // deny 时的原因（进审计）
  stop?: boolean;     // 「我放行，但后面不用问了」——照 Linux 的 NOTIFY_STOP
}
```

**P2 不做**，但结论保留，供 hook 轮直接使用。

### 2.2 从 Linux 学来的七条

| 做法 | 出处（Linux 6.12.110，行号基准见 `AGENTS.md` §3.1） | 对我们的含义 |
|---|---|---|
| **返回值协议**：不关心 / 赞成 / 别再往下叫 / 否决 / 赞成且收工；errno 能塞进返回值 | `include/linux/notifier.h:185-209` 的 `NOTIFY_*` 与 `notifier_from_errno` | 四态（放行/拦下/改了继续/我不管）够用；**要补一个"我放行，但后面不用问了"** |
| **顺序**：注册时按 `priority` **降序插入**；同一回调重复注册报错；同优先级可拒绝注册 | `kernel/notifier.c:25-45` 的 `notifier_chain_register` | 顺序用**显式优先级**，不靠猜。⚠️ 优先级**不能由插件自己写**（人人抢最高）⇒ **管理员在 Web UI 排** |
| **无限调用防护**：调用链用剩余次数封顶，并处理"回调里又注册了新回调" | `kernel/notifier.c:73-104` 的 `notifier_call_chain` | 我们跨 VM 风险更大 ⇒ 要**深度/次数上限 + 环检测**，超限 fail-closed |
| **两类链**：一类回调**不许阻塞**，一类**允许阻塞**；注册/注销还有上下文限制，且**注销不可以在调用链里做** | `include/linux/notifier.h:18-47`（原子链 / 阻塞链 / 原始链 / SRCU 链） | 钩子点分两类：**可裁决的**（必须能等，只能放在"进程上下文"式的点：登录、命令派发前）与**只通知的**（不许等：状态变化、装载卸载）。"处理中不许改登记"照抄 |
| **合成的粘性**：从默认值起，**第一个非默认返回值就短路**（后面的模块没有机会推翻前面的拒绝） | `security/security.c:994-1011` 的 `call_int_hook` | 可裁决链上：**先到的算数、后来者不能放宽**（fail-closed 方向） |
| **收件人与顺序在启动时定死**：顺序来自编译期内置序或启动参数，运行时只遍历这个静态定序且已启用的列表 | `security/security.c:1013-1016` 的 `lsm_for_each_hook`（顺序由 `ordered_lsms` 定） | 对应我们的"**清单声明 + 管理员批准 + 装载期定序**"，运行时只查表按序叫，**不接受运行时插队** |
| **阻塞式裁决的代价有先例**：fanotify 的权限事件让**发起方阻塞**等 listener 答复；另有"队列溢出"事件，溢出时权限事件只能拒绝 | `include/linux/fanotify.h:108-127` 的 `FAN_*_PERM` / `FAN_ALLOW` / `FAN_DENY` / `FAN_Q_OVERFLOW` | 每个裁决点都要有**等待预算 + 并发上限**，超时/溢出**一律 fail-closed（拦下）** |

### 2.3 等待与预算（跨 VM 的部分）

**两种发起方，性质不同**：

- **核心发起**（登录裁决）：核心在 Node 的 `await` 上等 ⇒ **暂停的是这一条流程，不是整个核心**（事件循环照常跑）；
- **插件发起**（A 征询 B 的意见）：A 挂在它自己那次宿主调用上 ⇒ 宿主去问 B、C 时它们都是空闲的。

**两种都不需要重入。** 唯一需要重入的情况是"**核心发起，而裁决方正是引发这次流程的那个插件**"（A 调 `exec.run`，而 `exec.before` 的名单里有 A）——**不支持**：该方本次**弃权** + 审计（`PLUGIN_BUSY` 是明确错误，不是死锁；不能定成"拒绝"，否则插件自己调一次就永久拒绝自己）。

**结论表**（P2 之后落地时照此实现）：

| 情况 | 处理 |
|---|---|
| 裁决方正忙 | **弃权 + 审计**（连续多次要告警） |
| 环形等待（A→B→A） | 因串行契约表现为明确的 `PLUGIN_BUSY`，**不是挂死**；链遍历用快照 |
| 预算 | **每方预算 + 整条链总预算叠加**，先到者算；等待**不耗 CPU**（挂起契约）但耗墙钟 |
| 超时 / 崩溃 | **视为拒绝**（fail-closed） |
| 处理期间被卸载 | **弃权 + 审计**（卸载是管理员的明确动作，不该顺带拒绝所有待裁决） |
| 链走一半被拒绝 | 发一条**回滚/事后通知**给已经答过的人（照 `kernel/notifier.c:122-129` 的 `notifier_call_chain_robust`）；配套纪律：**裁决方不要在 before 阶段做副作用** |
| 并行 | **可裁决链必须串行**（链式修改，顺序变结果就变）；**只通知链可以并行**；P2 之后第一版都串行 |

### 2.4 典型场景

**SSO 登录裁决**：插件在 `auth.login.before` 上注册裁决 → 核心在处理登录时按管理员排的顺序逐个回调 → 插件可以拦下、可以要求补一步（MFA）、可以放行 → **答复进核心决策**。

### 2.5 P2 期间核心唯一的"核心 → 插件"调用

不是事件、不进总线，方向相反：**依赖变更通知**。

- 时机：装载完成 / 卸载 / 重载 / 崩溃 / 禁用启用；
- 收件人：**声明依赖"出事那个插件"的插件**（不是"订阅"——可见性由依赖决定）；
- 内容：那个插件的状态与原因；**单向、不可裁决**；
- 埋点现成：`core/plugin/manager.ts` 的状态跃迁集中在一处，而"谁依赖谁"的查询也已经有了（现用于"被依赖时不许卸载/禁用"的反向保护）；
- 它顺手解掉 `plugin-lifecycle-design.md` 里挂着的两个待补项：**运行时依赖失效通知**、`OnPluginLoadedEvent`。
