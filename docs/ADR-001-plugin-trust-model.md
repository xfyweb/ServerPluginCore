# ADR-001: 插件信任模型 —— 零环境权力 + 宿主 API 为唯一边界

- 状态：**已接受**
- 日期：2026-08（项目初始化）
- 关联：ADR-002（运行时）、ADR-003（市场）、ADR-004（OS 底线）

## 背景

选型讨论中曾长期纠结"如何沙箱化插件"（WASM 隔离、容器、OS 用户矩阵、Deno 权限模型……），随后意识到陷入了错误的心智模型：

- 管理 Docker / nginx / 防火墙 / 数据库的插件**天生需要深权限**，沙箱化其"实现"可以，但沙箱化其"意图"不可能；
- 沙箱把安全押在"运行时永无漏洞"上（Deno 2025–2026 连续爆出权限绕过 CVE，见 ADR-004 证据表），押注不稳；
- 真正需要回答的问题是：**插件凭什么能碰 OS？**

## 决策

> **插件进程拥有零环境权力（zero ambient authority）：没有文件、没有网络、没有子进程、没有环境变量。插件唯一能做的，是通过宿主显式注入的桥接 API 向 Node 核心发起请求。**

推论：

1. **插件不是一个"程序"，是一个"客户端"**。对待它如同对待浏览器里的网页：认证、授权、输入校验、限流、审计——经典 Web 安全纪律直接适用，不需要发明新机制。
2. **沙箱议题整体消失**。既然插件摸不到 OS，就不需要容器 / WASM 隔离 / 多用户矩阵。安全工程的全部重心转移到**宿主 API 的审查与实现**。
3. **语言选型降级为纯开发者体验问题**。安全不押在运行时上——QuickJS（当前默认，ADR-005）与未来可选运行时（Deno / Node 子进程档）之争只剩"插件作者写着爽不爽"。

## 信任双档

| 档位 | 来源 | 权限 | 安装体验 |
|---|---|---|---|
| 官方档 | 官方市场，**签名验证完整性** | manifest 声明的权限原样放行 | 面板内一键安装，无警告 |
| 第三方档 | 自装 / 非官方源 | **强制降级画像**：默认禁 `exec` 模板之外的自由执行、fs 仅限插件数据目录、net 域名白名单 | 显著风险提示 + 展示降级前后对比 |

权限声明写入 manifest，**作为签名内容的一部分**——签名后篡改权限 = 签名失效。

## 签名链

- 签名对象 = **manifest + 代码哈希** 的整体；
- 面板**默认固定官方 registry URL + 官方公钥**；改源需醒目警告并显示"非官方源"角标；
- "官方插件"徽章 = 官方公钥签名验证通过才算数（防仿冒 / typosquatting）。

## 后果

- **宿主 API 必须"够用"**：插件能做什么完全取决于宿主提供的原语。SDK 不是装饰，是产品的另一半（exec 模板、受限 fs、定时器、事件总线、密钥存储、审计……）。
- **接口审查 = 安全工程中心**：每个宿主 API 方法按"被恶意插件调用会怎样"做威胁建模（见 api-contract.md 的危险原语策略）。
- **插件必然是薄适配器**：插件 = 胶水，把 nginx / docker / restic 等工具接进面板的 UI / RBAC / 审计，不重写工具。
- **残余风险**：运行时自身漏洞（爆炸半径靠"非 root"兜底，见 ADR-004）。
