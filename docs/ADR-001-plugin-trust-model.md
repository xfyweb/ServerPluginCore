## 背景

选型讨论中曾长期纠结"如何沙箱化插件"（WASM 隔离、容器、OS 用户矩阵、Deno 权限模型……），随后意识到陷入了错误的心智模型：

- 管理 Docker / nginx / 防火墙 / 数据库的插件**天生需要深权限**，沙箱化其"实现"可以，但沙箱化其"意图"不可能；
- 沙箱把安全押在"运行时永无漏洞"上（Deno 2025–2026 连续爆出权限绕过 CVE，见 ADR-004 证据表），押注不稳；
- 真正需要回答的问题是：**插件凭什么能碰 OS？**

## 决策

> **插件运行环境拥有零环境权力（zero ambient authority）：没有文件、没有网络、没有子进程、没有环境变量。插件唯一能做的，是通过宿主显式注入的桥接 API 向 Node 核心发起请求。**（默认档为进程内 QuickJS 沙箱；子进程档同理，能力面同样只有注入的桥接 API。）

推论：

1. **插件不是一个"程序"，是一个"客户端"**。对待它如同对待浏览器里的网页：认证、授权、输入校验、限流、审计——经典 Web 安全纪律直接适用，不需要发明新机制。
2. **沙箱议题整体消失**。既然插件摸不到 OS，就不需要容器 / WASM 隔离 / 多用户矩阵。安全工程的全部重心转移到**宿主 API 的审查与实现**。
3. **语言选型降级为纯开发者体验问题**。安全不押在运行时上——QuickJS（当前默认，ADR-005）与未来可选运行时（Deno / Node 子进程档）之争只剩"插件作者写着爽不爽"。

## 用户意图与双源授权（v4 修订）

**信任根前移到前端**：用户意图只能由**可信前端**捕获——插件后端与核心后端都无法感知用户意图，只有直接面对用户的 UI 能。

推论（不变量）：

1. 插件**不产生**意图，也不**解释**意图——只传递与使用凭证；
2. 插件 UI 里的"点击"**不构成授权**（可伪造），插件前端的任何请求都必须回到**核心渲染的确认窗口**才生效；
3. 核心前端是浏览器侧唯一意图捕获点；CLI 是**管理意图**的场所（只管插件与主题，不承载业务操作）；
4. 核心 UI 与插件 UI 必须**视觉可区分**，且安全关键 UI（确认窗口 / 来源角标 / 提权输入）的呈现**不受主题与插件影响**。

**授权两个来源**（长期与短期，互不替代）：

| 来源 | 谁签发 | 管什么 | 寿命 |
|---|---|---|---|
| **权限点** | 管理员（安装/授权时） | 插件**自主发起**的行为 | 长期 |
| **grantId** | **用户实时确认**（核心前端） | **用户此刻想做**的事：绑定 资源 + 操作 + 时效 + 受众 | 短期 / 一次性 |

- **核心自己做得到的操作不进插件**：用户确认后核心前端直接调核心 REST（删除文件、建立会话、重启服务……）；
- 插件只有在"它自己是执行者"时才介入，且涉及用户选中资源时**必须持 grantId**；
- 资源类操作**不受管理员作用域限制**（否则插件的限制会变成对用户的限制），但**安全底线仍受**：`/proc` `/sys` `/dev`、socket 与设备节点、管理员 deny 列表；**能合法提权（如 sudo 凭据）的动作不阻拦**。

**默认安全边界**（v4 定稿，intent-capture §7/§8）——把"折损率"当一等约束：

- 确认判据只有两条：**意图经不可信方转述**，或**点击时后果不可见**（二者皆否 → 静默 / 仅 toast）。确认不是"操作许可"，而是补足点击时看不见的信息；
- **对插件的自主行为，边界是"拒绝 + 可审计"，不是"打断用户"**——插件越界访问直接拒绝并告警，不弹窗。弹窗只服务用户意图；
- 权限点分 `auto` / `install` / `explicit` 三档：**安装即一次授权**（`install` 档读安装清单即生效），只有写宿主资源 / 执行模板 / 提权 / **出网（exec 模板或驱动插件端点，核心不提供网络原语）**需逐点授予；升级新增权限走**增量同意**；
- 读操作可以放宽，前提是**出网能力是唯一的 exfil 闸门**（intent-capture §6.3）——这条前提一旦被破坏，分档整体失效。**该前提的边界也在那里写死了**：核心不长网络原语，出网只有"模板"和"驱动端点"两条显式授权路径。

完整设计见 **intent-capture.md**；前端形态（核心 Web Shell + 声明式页面 + iframe 沙箱）见 ADR-005 v3。

## 来源与更新渠道（v3 修订）

**签名不再构成信任分级**：市场是唯一的签名主体，来源只决定"有没有更新渠道"与"安装提示强度"。

| 状态 | 判定 | 差异 |
|---|---|---|
| `anchored`（有源） | 包由 keyring 中某个**已启用的源**签名验证通过 | 有更新渠道：同一 `(origin, id)` 内可静默升级 |
| `unanchored`（无源） | 本地安装（`spc plugin install <dir\|file>`），不验签 | **无更新渠道**：每次更新都需人工安装并确认；安装提示更多 |

- **两档之间没有别的差别**：可申请任何权限点、可担任任何插件类型、可被授予任何等级——`secret` 级也只看管理员是否显式授予，**与来源无关**（v2 曾把"`secret` 级准入"挂在锚定上，v3 撤销）。
- **权限判定里没有来源这一维**：权限 = manifest 声明 + 管理员按点授予；来源既不放宽也不收紧权限（api-contract §6/§7）。
- 权限声明写入 manifest，**属于被签内容的一部分**——签名后篡改权限 = 签名失效。

## 市场签名（v3 修订）

- **渠道信任的签名者 = 市场**：发布必经市场；这与 apt 的仓库级签名一致——**客户端只以市场签名作为渠道信任**（plugin-signature-design.md §1）。
- **v4 追加：作者签名 = 依赖身份，不是信任层**：作者对**同一份 meta** 签一次，回答"**这是不是我依赖的那个插件**"（插件间定向调用 + 具名本地来源带来的需求，见 `events-and-hooks-design.md` §3.5）。它**不参与权限判定**、不改变安装提示强度、不提供更新渠道；**也不做**身份文档 / 命名空间委任（plugin-signature-design.md §1 推论 3、§3bis）。
- 签名对象 = **规范化后的元数据**（含载荷逐文件哈希），元数据覆盖 manifest；见 plugin-signature-design.md §2–§4。
- **信任根 = 管理员 keyring**，以**域名**为主键（公钥可由核心远程 TOFU 拉取，或管理员离线手填）；谁是市场由管理员决定，内置官方源只是初始条目，自建市场完全等价。
- 来源的显示标签 = 管理员给 keyring 条目起的别名；加源 / 改源永远是管理员的显式动作（防仿冒 / typosquatting）。
- 密钥轮换与吊销（链式"旧签新"、暂停机制）见 plugin-signature-design.md §6——**没有"紧急模式"开关**：是否属于泄露处置只由"本端信任的密钥是否仍在 `keys[]` 中"决定；`revoked[]` 只是给管理员看的信息，**不参与任何判定**。

## 后果

- **宿主 API 必须"够用"**：插件能做什么完全取决于宿主提供的原语。SDK 不是装饰，是产品的另一半（exec 模板、受限 fs、定时器、事件面、密钥存储、审计……）。
- **接口审查 = 安全工程中心**：每个宿主 API 方法按"被恶意插件调用会怎样"做威胁建模（见 api-contract.md 的危险原语策略）。
- **插件必然是薄适配器**：插件 = 胶水，把 nginx / docker / restic 等工具接进面板的 UI / RBAC / 审计，不重写工具。
- **残余风险**：运行时自身漏洞（爆炸半径靠"非 root"兜底，见 ADR-004）。
