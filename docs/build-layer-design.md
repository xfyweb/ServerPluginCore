# 构建层设计（打包流水线）

- 状态：**设计基线**（P2-2；§2 按 v2 修正重写，§7 的实测结论已验证，其余为实现契约）
- 关联：ADR-005 §6/§7（构建层 hook + 依赖管控）、**build-layer-evidence.md（实测证据与方法）**、plugin-signature-design §2–§5（元数据与签名）、module-emulation-design §10（builtin 联动）、plugin-lifecycle-design（产物如何被装载）、ROADMAP P2-2
- 定位：回答"**插件怎么从源码变成一个能装、能跑、可审查的单文件产物**"。

## 0. 一句话

构建层是**依赖管控的执行点**（ADR-005 §6）：能进产物的东西在这里定生死——**编译期不可达的代码，运行期就不可能出问题**。

## 1. 目标与非目标

**目标**

- `spcdev build [<目录>]` → 产物目录（`bundle.js` + 清单文件；**不产出 `plugin.meta.json`**，见 §2）；
  **作者签名是强制的**（"不存在无签名包"）⇒ 同一批还要有 `spcdev keygen`（见 §10）；
- 依赖闭包**静态解析 + 内建登记表校验**，违规**构建失败**（不是运行期拒绝）；
- 产物可被现有 `spc plugin install` 装载（`plugin-lifecycle-design` 不改契约）；
- **作者工作区那套工具与目录形态**（`keygen` / `plugin new` / `check` / `permission list` / `pack` / `dev` +
  `.spcdev/`）**同批定下并给出**，见 **§10** —— 没有真插件的验收等于没验收（用户 2026-09-25 的动因）。

**非目标（本阶段不做）**

- **签名**：市场密钥属 P4；本层只产出**可被签名覆盖**的元数据（逐文件哈希 + 规范化）；
- **市场发布**：上传/下载控制面属 P4；
- **可复现构建验证**：ADR-005 §6 提过"同输入同输出比对哈希"，本层只保证**确定性输出**（同样的输入产出同样的字节），**验证机制见 §2.1**；
- **依赖安装**：本层**不跑** `npm install`——依赖由开发者在插件仓库里自己管好，本层只做校验与打包。

## 2. 产物形态

**构建层不产市场签名；作者信封由构建层产出。** `plugin.meta.json` 是**市场来源校验**的载体（逐文件哈希 + 市场签名），
市场那一段属 P4 发布/签名流程；**作者信封**（`plugin.meta.json` + `plugin.author.sig`）由构建层产出（⑦b，见 §10.5 的 build 行）。本地构建的包没有"来源"可言，也就没有**市场签名**——这与"本地安装不验签"一致。

产物目录的布局**遵循 plugin-signature-design §2**：清单与载荷同级，将来 zip 一下就是 `.spc` 容器的载荷部分。

```
dist/                     ← 发布容器根（将来打包成 .spc 的内容）
├── manifest.json         清单：作者声明 + **构建器写入的产物事实**
└── bundle.js             单文件 ESM 产物（沙箱按源码文本加载，见 plugin-lifecycle-design §1.1）
```

**新增的条目写进清单文件，不写进元数据**（v2 修正）。由构建器写入的**产物事实**：

| 事实 | 落在清单的哪 | 来源（关键：都不是作者声明的） | 用途 |
|---|---|---|---|
| 真实解析版本 | `dependencies.npm[].resolved` | 构建器解析出的**真实版本**（不是 manifest 里写的区间） | 与作者声明比对，**不一致 → 构建失败**；于是声明从装饰性字段变成**可校验**字段 |
| 已登记内建的使用清单 | `build.builtins[]` | 第一道闸的判定结果 | **审查面**：一眼看到"这个插件用到了哪些宿主仿真模块" |
| 真实依赖闭包 + 逐包体积 | `build.closure[]`（`{name, version, bytes}`） | 构建器从 metafile 算出（不读声明） | 透明与归因：这插件里有哪几坨第三方代码、各占多少产物体积 |
| 产物体积 | `build.bytes` | 构建器 | 同上 |

> **对账的边界**（别把它想得比实际强）：**传递依赖不算不一致**（声明 `debug` 而闭包里还有 `ms` 是正常的，
> 闭包清单本身就是透明面）；**版本只在声明是精确版本时判**，区间只记录 + 在构建输出里点明"未核"
> —— 完整规则与仍未定的那条（要不要上 lockfile）见 §9-3。
>
> ⚠️ 这三个字段是**只增**进 `sdk/schema/manifest.schema.json` 的（`build` 与 `resolved` 都是可选字段，
> 作者不写）：产物清单要能被同一个校验器验过，否则构建出来的东西装不进去。

> **为什么这样分**：元数据被市场签名，是**来源**的证据；清单是**产物自己**的描述。
> 把"产物事实"放清单，是因为它是**构建器算出来的**——正好落在 ADR-005 §6 的原则上：
> **事实来源是构建器，不是 manifest 里的手写字段**。

### 2.1 确定性承诺（只管**载荷**）与**复核者流程**

> 用户 2026-09-26 定：**"确保实际代码产物一致就行了，签名什么的本来也不是复核者能产出的东西，无法复核。"**

**承诺**：同一份源码 + 同一版 `spcdev` ⇒ 包内**代码产物**逐字节一致。

| 文件 | 在承诺内？ | 为什么 |
|---|---|---|
| `bundle.js` · `manifest.json` | ✅ | 它们是**代码产物**：复核者能从源码重建并比对 |
| `plugin.meta.json` | ❌ | 含 `releasedAt`（缺省 = 构建时间，见下） |
| `plugin.author.sig` | ❌ | 复核者**没有私钥**，产不出同一个签名 |

> ⚠️ 措辞要精确：**Ed25519 本身就是确定性签名算法**（同一私钥 + 同一消息 ⇒ 同一签名）。
> "签名不可复核"的理由是**缺私钥**，**不是**算法随机性 —— 写成后者会引出"那换个随机化签名算法是不是就能复核了"的错误推论。

**⇒ 不为"容器字节一致"付代价**：固定 mtime、条目统一排序、压缩参数归一化、中央目录归一化都**不是要求**。
`pack`（⑦c）顺手能做到不反对，但**不为它加复杂度**。
⚠️ 别拿"不引新依赖"给 §10.6 的选择垫背 —— 那句 2026-10-12 核对后确认**不是用户拍板**（来路见 §10.6 与 §9-3）。

**复核者流程**（这是"确定性"的**消费者** —— 没有它，确定性只是个好看的性质）：

1. 从**源码**重建（同一版 `spcdev`）；
2. 算**载荷摘要**；
3. 与包内 `plugin.meta.json` 的 `files[]` **对账**（逐文件哈希；路径规范化、按 `path` 升序）；
4. 用清单里的作者公钥（`author.pub`）**验签** —— 验的是 `plugin.meta.json` 的规范化字节。

**`releasedAt` 的口子**：`plugin.meta.json` 必须有 `releasedAt`（授权判定锚点；市场只核对/拒签），
**缺省 = 构建时间**；要可复现就显式给 `--released-at <ISO>` 或 `SPC_RELEASED_AT`（后者优先）。

## 3. esbuild 配置决策（**基于 §7 实测**）

```js
await esbuild.build({
  bundle: true,
  format: 'esm',            // ESM-only 硬约束（ADR-005 §4）
  platform: 'node',         // ★ 见下，不是风格问题
  target: 'es2022',
  write: false,
  logLevel: 'silent',       // 错误自己归类成契约错误码，不透传 esbuild 文案
  absWorkingDir: pluginDir,
  plugins: [builtinRedirect],   // §5 第一道闸
});
```

**`platform` 的选择是安全决策**——实测三种取值的行为差异（矩阵见 §7）：

| platform | 内建引用 | CJS 包 | 结论 |
|---|---|---|---|
| `node` | **externalize，原样留在产物里**（`__require("tty")`） | 正常解析（用 `node` 条件，与作者测试的环境一致） | ✅ **选它**——引用留在产物里才**可扫描** |
| `browser` | 被"浏览器分支"绕开 → **构建通过但静默换了实现** | 正常解析（走 `browser` 条件） | ❌ 不可审计：你无法从产物看出原本要什么、被换成了什么 |
| `neutral` | 报 `Could not resolve` | **解析失败**（不适用 `main`/`exports` 的 node 条件） | ❌ 大量真实 CJS 包直接不可用 |

**为什么不用 browser 的"自动降级"**：它让构建通过，而作者以为自己在 node 语义下运行。某些包会拿到**完全不同的实现**（`crypto` 的多态填充、内存版 `fs`），行为不可预测；而且它**违背 fail-closed**——出问题时你看不出发生过替换。

## 4. 依赖闭包与能力检查（**不分信任档**）

```
1  解析**真实依赖闭包**（从入口出发，构建器自己算——不读 manifest 声明，声明不可信）
2  逐 specifier 判定：
     · 可内联的纯 JS 包              → 放行（内联进 bundle）
     · 已登记的沙箱内建（仿真模块）   → 重定向到对应 shim（§5 第一道闸）
     · 其它任何东西（未登记内建 / 原生 / 二进制 / 解析不到）→ **构建失败**
3  不跑任何依赖的 lifecycle 脚本（--ignore-scripts 等价）
4  真实闭包清单 + 体积写进产物元数据（透明与归因）
```

**这里没有"信任分级"**（ADR-005 §7 v2）：检查的产物只有两种——**能带**、**不能带**。理由：

1. **勾选拦不住任何东西**：依赖全部内联进单文件 bundle，装完之后不存在"加载依赖"这个动作；
2. **分级要靠"声明可信"，而声明不可信**：哈希只能证明"文件没被改"，证明不了"产物闭包 = 声明的清单"。用不可信输入做归档决策是把风险伪装成管控；
3. **原生/未登记内建是"丢进沙箱本来就会炸"**：把它写成"平台强制拒绝"只是把必然结果包装成策略。

**三条澄清**：

1. **判据不是"纯 JS"，而是"闭包里的每个 specifier 都能被解析成可内联的 JS 或已登记的内建"**。"纯 JS"无法静态判定、且绕起来容易（拆包、动态扩展名）；原生模块只是"永远解析不了"的那一类特例——所以**不需要单独定义"重型二进制"的体积阈值**；
2. **`node:*` 内建不是 npm 依赖**：它们走 §5 的仿真登记表。两者是**正交**的两件事——依赖检查管"能不能打包进来"，登记表管"宿主能不能提供它"；
3. **本层不产生任何"用户放行"动作**：既不勾选、也不记录批准。它只做构建期检查 + 把真实闭包写进元数据供人看。

## 5. builtin 校验：两道闸

### 第一道 —— 解析期重定向（esbuild 插件）

| specifier | 处理 |
|---|---|
| `@host/api` | **保留**（沙箱内由宿主注入，不由构建层处理） |
| 已登记的 `node:xxx` / 裸名内建 | **重定向到仿真模块**（构建层产出对应 shim，沙箱内走宿主注入） |
| 未登记的内建 | **构建失败**，文案必须指出"**沙箱尚未支持 X**"，而不是让作者以为代码写错（module-emulation-design §13-5） |
| 第三方包 | 正常解析 + 内联 |

> 重定向这一步是**必需的**：只是"允许"不够——`platform: node` 会把内建 externalize 成 `__require("fs")`，而沙箱里**没有 `require`**，即便登记了也跑不起来。

### 第二道 —— 产物断言（不信 esbuild 的报错）

**实测结论：不能只靠 esbuild 报错。** CJS 包的 `require('tty')` 在 `platform: node` 下**不会让构建失败**，它被转成 `__require("tty")` 兜底留在产物里（§7 证据）。

所以产物出来后还要断言：

```
产物里不允许出现 __require / require( 的**调用**
  —— 沙箱里根本没有 require；任何残留都说明有东西没被静态解析
  （辅助函数的定义行可以放过，调用点不行：`__require("tty")` 这类）
```

这条规则的好处是**自洽且不需要维护名单**：它拦的是"esbuild 没能静态解析"这个事实本身，而不管引用的是哪个内建。

## 6. 与签名、装载的关系

- 元数据**逐文件哈希**覆盖 `bundle.js`（`core/sources/canonical.ts` 已落地）→ 签名后篡改产物即可发现；
- **但哈希只能证明"文件没被改"，不能证明"产物与声明的依赖图一致"**——声明 `zod@3` 却打包了别的版本，哈希看不出来。**处置**（§2）：构建器把**真实闭包**与 `resolved` 写进清单，使声明**可校验**；哈希管"没被改"，构建器管"与声明一致"，两者互补；
- 装载侧**不改契约**：`plugin-lifecycle-design` 的入口解析已支持"记录/清单指定的入口"，本层只让 `entry` 指向 `dist/bundle.js`。

## 7. 实测记录（esbuild 行为，2026-09）

**为什么必须实测**：module-emulation-design §10-2 原本标着"实现细节待 P2-A 验证后落定，**不在此处假设 esbuild 行为**"。这份实测就是那个验证。

> 本节是**摘要**。完整数据、方法与"哪些结论后来被实测推翻"见 **docs/build-layer-evidence.md**；工具在 `tools/`（`esbuild-probe.mjs` / `gate-probe.mjs` / `dep-survey.mjs`），可重跑复核。

**方法**：跑具名脚本 `node tools/esbuild-probe.mjs`（自包含样本，不再需要手工造临时目录）。

```bash
node tools/esbuild-probe.mjs     # 参数矩阵（§1）
node tools/gate-probe.mjs        # 两道闸的可行性（§3）
```

样本与选它的理由：

| 样本 | 覆盖的情形 | 实测版本 |
|---|---|---|
| `zod` | 纯 ESM、不碰内建 | 4.6.5（dual 发布，`type: module` + `main: ./index.cjs`） |
| `node:fs` 直接引用 | ESM + `node:` 前缀内建 | 手写条目 |
| `path` 裸名引用 | 裸名内建（是不是内建取决于 platform） | 手写条目 |
| `debug` | **CJS** 包内部 `require('tty')` / `require('util')` | 4.4.3（无 `type` 字段 ⇒ CJS） |
| 伪造原生包 | `.node` + `binding.gyp` | 最小复现（不装需要编译的包） |

**矩阵**（`format=esm, bundle=true, target=es2022`）：

| 样本 | `platform: browser` | `platform: neutral` | `platform: node` |
|---|---|---|---|
| 纯 ESM（zod） | ok 753392B | ok 753392B | ok 753392B |
| `import { readFileSync } from 'node:fs'` | **FAIL** `Could not resolve "node:fs"` | **FAIL** 同左 | ok 100B，**`node:fs` 留在产物里** |
| `import { join } from 'path'` | **FAIL** `Could not resolve "path"` | **FAIL** 同左 | ok 93B，**`path` 留在产物里** |
| CJS 包（debug） | ok 15142B（**走浏览器分支**） | **FAIL** `Could not resolve "debug"` | ok 20216B（**`__require("tty")`/`("util")`/`("supports-color")`**） |
| 原生（`.node`） | **FAIL** `No loader is configured for ".node"` | **FAIL** 同左 | **FAIL** 同左 |

**四条结论**

1. **`platform: node` 会把内建 externalize，构建静默通过**（`node:fs` 只留 100B 产物）→ 若用它而不加第二道闸，"构建期即失败"就是空话；
2. **CJS 包解析不到的引用不会让构建失败**：esbuild 在 `node` 下把它降级成运行期兜底调用，**连 warning 都不给**（实测 `warnings` 为空）。
   **⚠️ 修正（v2）**：这里原本的表述把"内建"和"可选依赖"混为一谈——**未登记内建其实被第一道闸拦得住**（`onResolve` 对 try/catch 里的 `require` 同样触发，报错带依赖包内的行号）。真正只能靠第二道闸的只有两类：**解析不到的非内建可选依赖** 与 **动态 `require`**。详见 build-layer-evidence §2/§3；
3. **`browser` 的"能通过"是假象**：debug 的 `require('tty')` 之所以消失，是因为它按 `browser` 条件走了 `./browser.js`——**包被静默换了实现**。构建通过 ≠ 语义一致；
4. **原生模块的"必失败"是配置的产物，不是自动保证**：失败原因是 `No loader is configured for ".node"`——一旦有人为了让它过而配上 `.node` 的 loader，它就会被内联成二进制数据、构建通过。**必须把"esbuild 配置里永远不出现 `.node` loader"写成硬约束并加测试守住。**

**一个副产品（路线图输入）**：实测把"该先仿真哪些模块"从猜变成了数据——真实生态最常撞到的是 `util` / `tty` / `path` 这类**小内建**（`debug` 一条链就撞了三个）。P2-A 的 `path`/`util` 排得对，`tty` 是几乎零成本的补充。

## 10. 作者工作区与工具面（2026-09-25 定，用户拍板）

> 这一节回答的是"**作者怎么开发一个插件**"，与 §1–§9 的"怎么把源码变成产物"是同一层的两半。
> 定它的动因：累计到 ⑥c 的能力已经够跑通一条完整链路，但**没有真插件就没有真验收**（用户原话：
> "我前面实测了两下 CLI 就出来两个问题"）⇒ 构建层要顺手把作者要用的那套工具一起给出来。

### 10.1 工作区布局

```
ServerPluginCore/                      ← 克隆本体 = 插件开发工作区（**必须克隆本体**：类型与构建器都在里面）
├── core/ sdk/ tools/ docs/ …          ← 本体
├── plugin/                            ← 插件都在这里，一个插件一个目录
│   ├── hello/  · counter/             ← **随本体分发的两个示例**（前者综合、后者最小；README 与设计文档都引它们）
│   └── my-plugin/                     ← 作者新建的插件（**自己一个 git 仓库**）
│       ├── manifest.json              ← 作者声明：权限 + reason / exports / dependencies
│       ├── main.ts                    ← 入口（`import { fs } from '@host/api'`）
│       ├── package.json               ← 只为第三方依赖（构建层只**校验**闭包，不装）
│       ├── tsconfig.json              ← 让编辑器认识 `@host/api` / `@spc/sdk`
│       ├── README.md / .gitignore
│       └── dist/                      ← 构建产物（`bundle.js` + 带产物事实的清单；已 gitignore）
└── .spcdev/                           ← **开发期固定目录**（从待打包目录往上找最近的一个）
    ├── config.json                    ← 开发配置（作者 ID / 产物目录 / 默认来源 / 是否自动签名…）
    └── keys/{author.key,author.pub}   ← 作者私钥（`*.key` 已被 `.gitignore` 忽略）+ 公钥
```

**为什么插件放 `plugin/` 下**：本体的 `tsconfig.json` 的 `include` 里已经有 `plugin`，而 `@host/api` /
`@spc/sdk` 是 `sdk/*.d.ts` 里的 **ambient 模块声明** ⇒ 插件只要在 `plugin/` 下就**自动拿到类型**，
不需要 `paths` 映射、也不需要发布类型包。这是"必须克隆本体"最实在的理由。

### 10.2 `.spcdev/`：开发期固定目录

- **发现规则**：`spcdev build|pack|check|dev` 从**待打包目录**往上逐级找最近的 `.spcdev/`
  （`package.json` / `.git` 那种发现方式）⇒ "本体根放一份，一个作者一把钥管所有插件"成立，
  "某个插件目录里单独放一份"也成立，**近者优先**。
- **为什么不复用 `.spc/`**：那是**运行期状态**目录（`plugins.json` / `keyring.json` / `audit/` / `data/`）。
  把开发期密钥塞进宿主状态兜里，等于让"清状态"和"删密钥"变成同一个动作。
- `config.json` **可选**（除作者 ID 外全部有默认值）：
  `{ "outDir": "dist", "source": "local:default", "sign": true, "key": "keys/author.key", "author": "" }`。
- **作者 ID**（`author`）**是唯一没有默认值的一项**：它就是清单里 `@<作者 ID>/<名字>` 的 `@` 前缀
  （= `sdk/types.ts` 的 `Manifest.id` 那个**发布者命名空间段**，同一件东西的两种叫法：工具面叫"作者 ID"、
  清单面叫"发布者命名空间"）。由 **`spcdev keygen` 问一次**写进来，之后 `spcdev new` 直接取用
  —— 于是**不再有 `--id`**：插件的 id 恒等于 `@<配置里的作者 ID>/<目录名>`。
  ⚠️ 没声明又没显式 `--author` 时**一律拒**（`AUTHOR_ID_REQUIRED`）：身份是一次性决定、且会印进插件 id，
  工具**不猜**（`git config user.name` 只用作交互提问时的默认答案，绝不顶替回答）。
- `.gitignore`：本体与插件模板都忽略整个 `.spcdev/`（私钥已被 `*.key` 规则覆盖，整目录忽略是双保险 ——
  防手滑命名成 `author.key.txt`）。

### 10.3 插件目录与 git

- **每个插件是独立仓库**（作者自己 `git init` / 推远端）；**本体仓库忽略 `plugin/*/`**，
  只放行随本体分发的两个示例（`plugin/hello/`、`plugin/counter/` —— ⚠️ 少放行一个，往它里面加文件就会被**静默忽略**，
  `git status` 也看不到）。于是本体 `git status` 永远干净，作者也不必为了写插件去 fork 本体。
- 第三方依赖由**作者自己** `npm i`（各自的 `package.json` / `node_modules`）；构建层**不跑安装**（§1 非目标），
  只解析真实闭包并写 `resolved`（§2）——声明与实解不一致即**构建失败**。

### 10.4 作者密钥与作者 ID（`spcdev keygen`）

```jsonc
// .spcdev/keys/author.key  —— chmod 600，永不进包（*.key 已在 .gitignore 里）
{ "schema": 1, "alg": "ed25519", "seed": "<base64 32B>",
  "pub": "<base64 裸 32 字节>", "fingerprint": "sha256:…", "createdAt": "…" }
```

- **默认无 passphrase**（它保护的是"身份连续性"，不是数据机密性）；将来要加，加一个可选字段即可（只增不改）。
- 公钥同时写一份 `author.pub`（便于复制给别人 / 贴到 README）；指纹按 §4 的全局规则算，**打印出来让人抄下来**。
- 只产**作者签名**（`plugin.meta.json` 的 `authorPub` + `plugin.author.sig`）；市场签名属 P4。
- **作者 ID 也是这一步问的**（2026-09-25 用户定）：钥里没有名字，而"这段 id 属于谁"必须有个地方写清楚 ⇒
  `keygen` 问一句（默认答案取 `git config user.name` 归一化后的值，回车即用）、写进 `config.json` 的 `author`。
  - **先写配置、再产钥**：反过来的话，配置写失败会留下"有钥但没身份"的死角（下次 keygen 被 `AUTHOR_KEY_EXISTS` 挡住，
    只剩手改配置或 `--force` 换钥两条路）；这个顺序最坏只是"声明了身份还没钥"，重跑一次就接上。
  - **钥在、作者 ID 没登记 ⇒ 只登记，绝不碰密钥**（拷 `keys/` 换机器的常见场景）；配置里已有作者 ID 时，
    跑 `keygen` 又回到"换钥要 `--force`"的老规矩。
  - **非 TTY（脚本 / CI）不给 `--author` ⇒ 拒**（照 ⑥b"非交互要给 `--yes`"的先例）：不拿 git 推断值顶替回答。
- ⏳ **⑦b 必须核对"清单里的作者 == 工作区作者 ID"**（用户 2026-09-26 定；**先记着，⑦b 时做**）：构建读的是**工作区密钥**，
  而插件挂谁名下写在 `manifest.id` 里 ⇒ `spcdev build` 要核对 `manifest.id` 的作者段等于 `config.author`；
  不符即**构建失败**，`config.author` 为空同样失败（复用 `AUTHOR_ID_REQUIRED`）。理由：两处不一致时产出的包就是
  "**用 A 的钥签了挂在 B 名下的插件**"，而那是发出去就改不回来的事。
  ❓ 两个细节留到 ⑦b 一起定：新码叫什么（倾向 `BUILD_AUTHOR_MISMATCH`）；`spcdev check` 是否也报（建议报 warn，build 才是硬闸）。

### 10.5 工具清单

| 工具 | 档 | 状态 | 做什么 |
|---|---|---|---|
| `spcdev keygen` | **必须** | ✅ ⑦a | **问一次作者 ID 写进 `.spcdev/config.json`** + 生成作者密钥到 `.spcdev/keys/`（§10.4） |
| `spcdev new <名字>` | **必须** | ✅ ⑦a | 脚手架：按模板在 `plugin/<名字>/` 生成最小可跑插件（清单 + 入口 + tsconfig + README + .gitignore）。**id = `@<配置里的作者 ID>/<名字>`**（没有 `--id`；换作者用 `--author`）。⏳ 发布 `create-spc-plugin` 到 npm（"没克隆本体也能起一个"）记进待办 |
| `spcdev build [<目录>]` | **必须** | ⏳ ⑦b | bundle + **两道闸**（§5）+ 产物事实写清单（§2）+ **作者签名** + **核对清单作者 == 工作区作者 ID**（§10.4）；**载荷**同输入字节一致（§8 第 8 条 · §2.1） |
| `spcdev check [<目录>]` | 便捷 | ✅ ⑦a | **只校验不打包**（清单 schema + **权限点对账** + 导入面：内建是否已仿真 / 第三方是否解析得到），秒级反馈，给编辑器与 CI 用 |
| `spcdev permission list` | 便捷 | ✅ ⑦a | 列出本机**已注册的权限点**（冻结表；动态族只给形状）；纯本地、不需要 daemon |
| `spcdev pack [<目录>]` | 便捷 | ⏳ ⑦c | 打 `.spc` 容器（§10.6）；本地分发与"全链路验收"要用 |
| `spcdev watch [<目录>]` | 稍后 | ⏳ ⑦c | watch 重建 + 自动 `plugin reload`（走已有管理通道）；不做 HMR，就是省掉手敲两条命令 |

> **两个命令、两份受众**（2026-09-25 用户拍板）：**`spc` = 管理面**（status / daemon / plugin / source；多数要 daemon；
> P5 起随核心运行时一起分发）· **`spcdev` = 作者工具**（本节这一切；全程本地；**必须与这份仓库同版本**）。
> 为什么不做成"一个命令下的子指令集"：受众、前提、发布节奏都不同 —— 混在一个入口里迟早出现"工具与本体不一致"
> （工具说没问题、本体说不行），而那是本项目最难查的一类错。
>
> **代码落点**（⑦a 已落地）：新顶层 `build/` —— `workspace.ts`（`.spcdev/` 发现 + 配置）· `keys.ts`（作者密钥）·
> `scaffold.ts`（脚手架）· `check.ts`（自检）· `permissions.ts`（权限点清单）· `apimap.ts` + `api-permission-map.json`
> （**权限映射快照**）· `cli.ts`（子命令实现 + `runDevCli` 分发）。两个入口：`core/cli.ts`（`spc`）与
> `core/cli-dev.ts`（`spcdev`），共用 `core/about.ts`（about 打印**仓库根 + 启动方式**）。
> **短命令**：仓库根跑一次 `npm link` ⇒ 任何目录都能直接 `spc` / `spcdev`（`pnpm` 没有 `link --global`；
> 不 link 也能用 `pnpm spc` / `pnpm spcdev`，插件模板的 `package.json` 里也带了 `spcdev` 脚本）。
> ⚠️ 权限映射是**生成物**：改 `core/hostApi.ts` 后跑 `node node_modules/tsx/dist/cli.mjs build/refresh-api-map.mts`；
> 守卫用例（`build/__tests__/workspace-keys.test.ts`）会重抽一遍比对，漂了就红。

**`spcdev check` 的"权限点对账"**（用户 2026-09-25 要求，两向都报）：静态扫入口用到的 `@host/api` 成员 →
映射到**权限点族** → 与清单 `permissions[]` 比对：

- **代码用了、清单没声明** ⇒ 报（运行时会撞 `NOT_DECLARED`）；
- **清单声明了、代码没用** ⇒ 也报（可能是升级后的残留；`host` / `explicit` 档尤其值得清理）。

⚠️ **能力边界（必须写进输出与文档）**：① 路径决定的档位**静态判不出**（`fs.read.data` 还是 `fs.read.host`
取决于运行期路径）⇒ 只报到**族**；② `plugins.call` / `events.subscribe` 两族的点名里带引用，
静态只能报"用到了跨界调用"，精确对齐要看清单的 `dependencies.plugins[].call`；③ 它**不代替**运行期判定。

**明确不做**：运行期装依赖（`npm i` 是作者的事）· `.node` loader（§7 结论 4 的硬约束，要有测试守住）·
依赖分级勾选（ADR-005 §7 v2 已否）· HMR。

### 10.6 `.spc` 容器与**两条装载路径**

- **容器 = 标准 zip，后缀 `.spc`**（`plugin-signature-design.md` §12-1 的待定项就此定下）。
  **这条的来路要说清**（2026-10-12 核对早期记录后修正）：**2026-09-11 就定了两件事** ——
  ① 用 **zip** 容器（不是自定义二进制：签的是**安装意图**，不是容器字节流；包会经 CDN / 镜像 / 用户重打包，
  压缩方式、mtime、条目顺序、权限位都会变）；② **校验不依赖容器字节**。
  ⚠️ 而"**手写 local file header + central directory（`zlib` 做 raw deflate）**"这一条实现方式，
  出处是 2026-09-25 **我那张提问卡片**：选项写成"确定性 zip（**手写 ~80 行、无新依赖、时间戳固定 ⇒ 字节一致**）"，
  把**四件事捆成了一个选项** —— 用户点的是"zip"，记录里却落成四件都拍过
  （⚠️ **工具卡片不进会话导出** ⇒ 事后从 transcript 里查不到它问过什么，只能从这条 git 记录往回推）。
  随后 9/26 用户砍掉"字节一致"、9/27 我又把本节的"理由"改写成"不引新依赖"（于是它成了唯一理由）。
  ⇒ **实现方式（2026-10-12 定，同日落地）：用成熟 zip 库，不自研字节层** —— 写 `yazl`、读 `yauzl`。
  判据两条：① 9/11 那条精神（"自定义二进制唯一的收益是省几十字节，代价是一辈子的解析器和兼容坑"）；
  ② **解开 `.spc` 的那一半在 daemon 里处理的是别人给的包 ⇒ 不可信输入**（zip-slip、zip 炸弹、zip64、路径编码…），
  正是 `AGENTS.md` §2 依赖政策里"不可信输入上的解析优先用成熟库"那一格。
  **`spcdev pack` 已落地**（`build/pack.ts`）：产物写到 **`<插件目录>/release/<插件名>-<版本>.spc>`**
  （不丢在插件根目录 —— 那里已经挤着清单 / 源码 / `dist/` / `.spcdev/`，发布物混进去更难找）；
  写 zip 时顺手固定 mtime/mode 并排序 ⇒ 同一份载荷两次打包字节一致
  （**白拿，不是承诺**）；打包前三道检查（产物目录在不在 / 信封齐不齐 / **信封与载荷是否一致**）失败即 `PACK_*`（退出码 3）。
  **互操作实测**：系统 `tar`（bsdtar）能列出并解出我们的 `.spc`，逐文件哈希与产物目录一致
  ⇒ 是**标准 zip**，不是只有自家读者认得。
  ⚠️ **已知空白（不是 pack 的疏漏）**：载荷现在只有 `bundle.js` + `manifest.json` + 信封三件套 ——
  **静态资源（`web/**` 之类）还没有声明字段**（`frontend` 只有 `mode`），"资源怎么进产物"**尚未设计**（属 P3 前端形态那一档）。
  ⚠️ 时间戳固定之类只是**顺手**，**不是**确定性承诺的一部分：承诺只管**载荷内容**（§2.1），
  容器字节（mtime / 条目顺序 / 压缩参数）**不在承诺内** —— 签名本来也不覆盖容器
  （`plugin-signature-design.md` 的"不做自定义二进制容器"那条）。
  载荷就是 §2 的产物目录（清单与载荷同级），`plugin.meta.json` / 签名将来由市场追加。
- **两条入口，同一条安装管线**（身份 / 授权 / 审计 / 记录语义完全一样，只有载荷放哪不同）：

| 入口 | 载荷在哪 | 用途 |
|---|---|---|
| `spc plugin install <目录>` | **就地**（作者给的 `dir`） | 开发：改源码 → `reload` 即生效 |
| `spc plugin install <文件.spc>` | **托管副本**：daemon 解包到 `<STATE_DIR>/packages/<来源>/<id>/`，`record.dir` 指向它 | 分发：产物不可变 ⇒ 与源目录无关；市场安装流以后走同一条路 |

**"载荷放哪"决定了三处生命周期语义上的差别**（都写在 `PluginRecord.hosted` 这一个标记上）：

| 动作 | 就地安装（`hosted` 缺省） | 托管副本（`hosted: true`） |
|---|---|---|
| 重装 / 升级 | 作者自己的目录，我们**一个字节都不动** | **整体替换**副本（那是我们的目录） |
| **卸载** | 记录删掉，**目录保留**（那是作者的仓库） | 记录删掉，**副本一起删** —— 记录都没了，副本就是孤儿 |
| **换源**（`reanchor`） | 目录**不搬**（它跟着作者走，不跟着来源走） | 副本**搬到** `<packages>/<新来源>/<id>/`，`record.dir` 跟着改 |

> 删副本的判据是"**两个条件都满足**"：记录标了 `hosted` **且** `dir` 确实在 `<STATE_DIR>/packages` 之内
> —— 纵深防御，删错目录不可逆。
> 数据目录与配置值则是另一件事：**卸载一律保留**（见 `plugin-lifecycle-design.md` §12-3）。

**解包是"不可信输入"那一半**（`core/sources/unpack.ts`，用 `yauzl`）：路径形状（绝对路径 / 盘符 / `..` / `.` /
空段 / 反斜杠规整）、条目数与解压体积上限、符号链接、加密条目、重名条目，**逐条 fail-closed**；
任何一步失败就把**整个暂存目录删掉**（半个解出来的包比没有更危险），被拒的包在名册里**一个字都不留**。

- 从 `.spc` 安装是**本地语义**（不验市场签名 ⇒ `unanchored`、没有更新渠道）——
  正好就是 `reanchor` 的"先本地发放、后上市场"场景。

### 10.7 全链路验收（真插件，不是夹具）

`spcdev keygen` → `spcdev new demo` → 写点真代码（权限 + 一个端点 + 一次跨插件调用）→ `spcdev check` →
`spcdev build` → `spcdev pack` → `spc plugin install demo.spc` → 真跑起来（daemon + 审计）→ 改一行 → `spcdev dev`/`reload` →
`spc source add` + `reanchor` 搬桶 → 面板/CLI 看到的能力与授权都对。
**这条链路跑通才算构建层验收**（§8 的 9 条是单元级，这一条是端到端）。
